# 跨项目自动化模拟人工测试提效方法论

> 建立时间：2026-09-01
> 性质：跨项目复用方法论，不是 ProFlow 专属流程。
> 目标：在不削弱真实用户路径和真实外部系统验证的前提下，把“发现问题 → 修复 → 再验证”的循环压到最短。

## 1. 核心原则

自动化模拟人工测试必须同时满足两件事：

1. **语义上像真人**：走真实产品入口、真实 UI、真实 CLI、真实外部服务；不能靠内部状态注入把系统“修成成功”。
2. **执行上不像手工**：已经证明稳定的机械动作必须脚本化、原子化、可续跑；不能每轮重新研究怎么点、怎么输、怎么清理。

固定主循环：

```text
真实用户 Journey
→ 失败现场保存
→ root cause 定位
→ 最小修复
→ changed + affected targeted gate
→ 回到 SAME SCENE 重放
→ PASS 后继续下一用户步骤
```

最重要的提效思想不是“所有东西并发”，而是：**不要重复已经证明成功且与本次修复无关的昂贵步骤。**
## 2. 两级测试模型：FAST REPLAY 与 FULL FRESH

任何包含安装、配置、浏览器、外部服务的项目，都应在第一天定义两种测试强度。

### FAST REPLAY：日常修复循环

```text
只升级 changed / affected artifact
→ 回到原失败步骤
→ 重放该步骤及其必要下游
→ 最小 lifecycle / readiness 验证
```

目标：尽量做到几十秒到 1～2 分钟，而不是每个 Bug 都从零部署。

FAST REPLAY 禁止：重新 Fresh、重装全部依赖、重做已 PASS 的 OAuth/浏览器创建/远端资源创建、重跑全仓 Gate。

### FULL FRESH：阶段最终验收

```text
真实 latest artifact
→ 真正 Fresh 环境
→ 完整用户主链
→ 真实外部系统
→ 最终 readiness / acceptance
```

FULL FRESH 不允许为了提速裁剪真实用户 Journey，但只在大阶段收口、release 验收、最终产品验收时运行。工程 Gate 可以缩范围，最终真实用户链不能缩范围。
## 3. SAME SCENE 恢复：失败后不要从头来

固定规则：**失败停在哪一层，就从哪一层恢复。**

```text
UI mutation 失败
→ screenshot-first
→ 判断当前可见状态
→ one controlled retry
→ 仍失败则定位 root cause
```

```text
远端 mutation timeout / UNKNOWN
→ 禁止重试 mutation
→ 查询远端 authority / 本地 durable state
→ 判断 mutation 是否实际成功
→ 从已知真实状态继续
```

install / publish / deploy / create / migration 等非幂等动作必须遵守该规则。UNKNOWN 是“需要恢复真值”，不是“从头再跑”。

已经通过的 Browser、Tunnel、Model、身份创建等昂贵域，若与当前修复无关，不得为了图省事重新执行。

## 4. UI 自动化：稳定路径一旦成立就冻结

真实 UI 验收要求用户语义不变，但执行动作应原子化：`activate → locate current bounds → mutate → verify`。

- 普通 Web DOM：优先浏览器自动化。
- 浏览器内部页、系统文件选择器、原生确认框：使用系统 Accessibility + 实时 bounds + 系统输入事件。
- 禁止长期依赖固定截图坐标。
- 用户可见异常必须先截图，再查后台状态。
- 已经稳定运行的复杂 UI 创建流程应标记 `FROZEN / DO NOT TOUCH`；性能优化优先改它外围，避免为了几秒钟破坏稳定性。

### 4.1 稳定 UI Helper 必须唯一，禁止现场重新发明

一条真实 UI 路径一旦验证稳定，必须沉淀成仓库内**唯一可执行 helper**，后续 FULL FRESH / FAST REPLAY 只调用它。禁止因为当前 Chat、工具上下文或临时脚本方便，就重新写第二套 `/tmp` Swift、AppleScript、expect 或固定坐标方案。

固定状态机必须是：`locate → mutate → observe visible state change → verify`。`AXPress=success`、键盘事件成功发送、命令 exit code=0 都只能证明“事件已发出”，**不能证明 UI mutation 已完成**。系统文件选择器尤其必须把“进入目标目录”和“点击 Select”拆成两个可观察阶段，中间等待真实 UI ready；确认 bubble 不暴露 AX 时，应使用已经验证的默认键盘确认，而不是猜测另一个按钮坐标。

CLI TTY 自动化同样必须是**具体 prompt 的单次状态机**：每个公开问题只响应一次；禁止 `看到 Yes 就 Enter` 之类宽泛匹配，也禁止用方向键猜默认选项。若测试机器人自身发生定位错误、脚本编译错误、焦点错误或错误恢复，该耗时必须记为 `HARNESS_OVERHEAD`，不得计入产品 happy-path 性能基线。

成熟 UI helper 的变更本身视为高风险测试基础设施变更：必须单独验证 helper，再进入 FULL FRESH；不能一边跑最终验收一边现场调试 helper。

## 5. 长驻进程与测试 Harness

测试框架必须先理解产品 lifecycle，而不是把“命令没有退出”自动判成 hang。

如果 `start` 本身是 foreground owner：

```text
start
→ 识别明确 READY/启动完成信号
→ 保留 owner session，不等待退出
→ 新 session 执行 status / smoke
→ public stop 请求 owner graceful shutdown
→ 验证 owner 真退出
```

禁止用 `kill -9` 冒充正常 stop，也禁止用 `| tee` 等可能被子进程继承 FD 的包装方式判断命令是否结束。

长进程一次启动，保存 PID/session；低频读取状态。无新 stdout、Blocked=true 不等于失败。

## 6. 性能测量：先拆阶段，后优化

每个昂贵命令必须输出或被 harness 记录 phase elapsed time，而不是只记录总耗时。

推荐至少记录：`preflight / discovery / download-or-install / validation / external-probe / UI-action / final-readiness / total`。

必须区分：

- 产品耗时 vs 测试工具/MCP 等待耗时；
- cold cache vs warm cache；
- subsystem 本身耗时 vs 后续步骤被错误归因的耗时；
- 一次失败 recovery 的耗时 vs 正常 happy path。

发现慢点后先 profiling，再改并发/timeout；禁止凭感觉把所有请求全并发。
## 7. 工程 Gate 与真实 E2E 分层

修复循环默认只验证 changed + affected 范围：

```text
CodeGraph / dependency analysis
→ targeted regression
→ affected package test + typecheck
→ 回原真实场景
```

全仓 test/build/architecture/publishability 只在大阶段、公共合同变化、release transaction 明确需要时运行。不能每修一个 Bug 都跑整仓。

真实 E2E 与工程 Gate 是两条不同证据链：测试全绿不能替代外部 reality；真实 UI 看起来正常也不能替代代码回归 Gate。

## 8. 新项目第一天就应建设的自动化资产

1. `fresh/reset` harness：安全白名单、ownership 校验、fail-closed。
2. `fast-replay` harness：从已知状态重放最小用户链并统一计时。
3. `full-fresh-e2e` harness：完整最终用户 Journey，逐 phase 落 timing/evidence。
4. authority recovery：为 install/publish/create/deploy 等非幂等 mutation 定义 UNKNOWN 恢复查询。
5. browser/system UI helpers：把已经稳定的点击、文件选择器、确认框操作原子化。
6. lifecycle owner model：明确 start 是短命命令还是 foreground/daemon owner，测试框架按真实合同驱动。
7. evidence whitelist：只读允许的状态文件/字段，禁止递归 dump secrets。
8. performance baseline：第一次 cold、第二次 warm、FAST REPLAY 三组基线都记录。
9. stable-flow freeze list：成熟但复杂的 UI/外部系统流程列为 DO NOT TOUCH，避免无收益重构。
10. one source of truth：把上述规则放到仓库长期文档，新 Chat/新 Agent 开始执行前先读取。
## 9. ProFlow 2026-09-01 实测样本：为什么这套方法有效

这组数字只作为方法论证据，不作为其它项目 SLA：

```text
Cold Fresh platform install     250.500s（早期冷缓存）
Warm Fresh platform install      52.089s（优化前 warm baseline）
Final Fresh platform install      58.866s（真实 latest，23/23）
Final Browser Fresh helper        18.998s
受影响包原地升级                   3.91s（dev-tunnel 示例）
历史 FAST lifecycle replay       ~49.4s + backstage probe
最终完整 lifecycle replay         59.49s（含两次 start、repeat setup/status、stop/final status）
最终校准 backstage 单独闭环       29.606s（额外 start + probes + stop）
```

一次总 `setup≈220s` 经 profiling 后拆为：模型真实 capability probe 约 66～67s，三个 Custom GPT 创建/校验约 143s，其余为编排开销。由此得到硬经验：**没有 phase timing 就很容易优化错对象。**

Registry profiling：`npm search≈4.45s`，23 个 `npm view` 在 4 workers 时约 37.75s，8 workers 时约 30.86s，因此只做 bounded `4→8`，没有改成无限并发。

最终验收还冻结了一个重要规则：**probe 必须按当前服务合同校准，不能沿用历史 HTTP 断言。** ProFlow 当前 Model Runtime `/ready` 受 transport credential 保护，所以匿名 401 是安全合同而不是“不就绪”；Agent Gateway `/ready` 是公开 readiness，所以 Tunnel `/ready=200` 才是正确结果。最终 backstage 使用 `Model /health=200 + authenticated /ready=200`、其它本地 runtime `/ready=200`、公网 Tunnel `/ready=200 + protected /actions/...=401/AUTHENTICATION_FAILED`，全部 PASS。

CLI TTY 自动化也新增一条可迁移经验：设置父终端宽度不等于设置 Expect 创建的 child PTY。对 Clack 等会按终端宽度重绘的交互，必须在**真正执行产品命令的 child PTY 内**先设置 rows/columns，再 `exec` 产品命令；否则提示可能逐字符换行，导致稳定语义 matcher 也无法命中。

复杂且已经稳定的 3 GPT 浏览器创建路径已明确冻结：`FROZEN / DO NOT TOUCH`。循环提速来自外围 harness、受影响包升级和 SAME SCENE recovery，不来自重写稳定 UI 创建动作。

同日后续 FULL FRESH 又提供了反例：Fresh cleanup `8.581s`、global latest install `9.546s`、Fresh `platform install=105.855s`（Registry `40.1s` / dependency sync `41.0s` / local validation `3.9s`）这些**独立 phase timing 有效**；但 Browser install/uninstall 与 TTY prompt 驱动因临时 helper 错误发生多次恢复，因此该轮“从 Fresh 到 READY”的总耗时被判定为 **INVALID_FOR_HAPPY_PATH_BASELINE**。这条反例进一步冻结：性能基线必须能剔除 `HARNESS_OVERHEAD`，不能因为最终功能 PASS 就接受被测试机器人错误污染的总时间。

## 10. 新项目可直接复制的执行口令

```text
先完整定义真实用户 Journey 和 PASS 条件。
先测 cold/warm/fast-replay 基线，再谈优化。
失败先保存现场；UI 异常 screenshot-first。
非幂等 UNKNOWN 先恢复 authority，绝不盲重试。
只修 root owner，只跑 changed + affected Gate。
修复后回 SAME SCENE，不从头 Fresh。
稳定 UI 流程第二次出现就 harness 化，成熟后冻结。
最终 FULL FRESH 不裁剪；日常 FAST REPLAY 不重复昂贵已通过域。
所有昂贵 phase 必须有 elapsed time。
```

这份方法论应在未来任何带真实 UI / CLI / 外部服务 / 部署流程的项目中作为自动化验收设计输入，而不是等项目变慢以后再补。
