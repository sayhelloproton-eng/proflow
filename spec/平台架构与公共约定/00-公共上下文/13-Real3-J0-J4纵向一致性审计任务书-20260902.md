## 3. Real-3 J0～J4 业务语义

```text
J0  3 Role/GPT 已可用于真实 Task
J1  New Task → PENDING → Product/Dev/Test Worker + Conversation Binding → Product 需求沟通
J2  用户确认 → startTask → 前置条件校验 → first Node READY
J3  READY Node → Observer → Locate Worker/Conversation → Restore → WAKE 真正提交
J4  Worker 收到 WAKE → 自主 Worker Turn → Reason → Action/Owner API/Execution → Result
```

必须严格区分 `Role != Worker`、`WAKE success != Node success`、`Browser API call success != message truly submitted`。
## 4. 审计优先级

P0：

1. **Task / Node 状态机与 Orchestration**：Task 真值、Node 真值、PENDING→启动、首个 READY、幂等与 fail-closed。
2. **Role → Worker → Conversation 持久身份链**：同一 Role 服务多 Task、每 Task 独立 Worker、稳定 `workerRef`、Conversation binding 持久化、部分失败只补缺失项。
3. **Observer → Locate → Restore → WAKE**：谁观察 READY、谁选择 Worker、谁定位 Conversation、谁触发 restore、WAKE 如何去重、何时算真正提交成功。
4. **WAKE → Worker Turn → Owner API / Action**：Worker 如何取 Task/Node/Requirement/Context；Action loop 是否由 GPT 原生继续，而不是 Browser 反复“点继续”。

P1：Browser Carrier 的 restore/submit 真值；Agent Gateway / Platform Host 的上下文/Owner API 边界；Execution Runtime 在 J4 的最小接入。

P2：Deployment/Chrome/Tunnel/Model 基础设施。只有审计发现它们真实破坏 J0～J4 合同时才上升，不做泛化复审。

## 6. 每个 J 必答问题

J0：3 个 Role/GPT 的“已创建”与“可被真实 Task 使用”是否有清晰边界？Role credential、carrier、Action/Owner API readiness 的正式 owner 与测试在哪里？

J1：New Task 的唯一入口是什么？Task 为什么是 `PENDING`？三个 Worker 何时创建/识别？Worker 与 Conversation 如何持久绑定？若 Product/Dev 成功、Test 失败，是否只补 Test，绝不回滚/重建已有 Worker 或 GPT？

J2：用户确认后谁调用 `startTask`？Requirement、3 Worker binding、Task state/version/idempotency 的前置检查在哪里？谁有权生成 first Node，谁有权把它置为 `READY`？重复 start 是否安全？

J3：哪个 Observer 看见 READY Node？如何从 Node 找到正确 `workerRef`、Role 与 Conversation？Restore 的 owner 是谁？WAKE payload 是否保持最小？怎样证明“正确 Conversation 的消息真实 submit”，而不是仅仅 API 返回成功？WAKE 如何做幂等/去重/恢复？

J4：WAKE 后 Worker Turn 的边界是什么？GPT 如何通过 Owner API / Action 读取大上下文？Browser 是否在 WAKE 后退出主循环？是否存在 Browser 反复驱动 Agent Loop 的旧路径或 bypass？Execution Runtime 在本阶段只是最小能力入口还是被错误要求承载后续 Real-4/5 能力？

对每个问题，都必须给出：规范文件、Test Plan case、Formal Case ID、Executable Test 文件/测试名、生产代码文件/symbol、真实调用方向，以及一致/不一致结论。
