### 当前唯一目标：部署成功，不验证完整业务系统可用

当前这轮只闭环 **Deployment / Fresh Workspace**。部署成功不是单纯“命令 exit 0”，而是下面六个维度同时达到当前部署阶段要求：

1. **技术闭环**：真实 Fresh Workspace 能完成 `platform install → platform setup → platform start → platform status`，部署必要状态成立且没有 Fake READY / Fake SUCCESS。
2. **CLI 产品质量**：输出、错误、进度、下一步和成功摘要合理；不把 23 个内部模块 traversal、shared facts、package CLI 等实现细节甩给普通用户。
3. **交互与用户心智**：一次只暴露当前真正需要处理的 root prerequisite；用户能理解“现在在哪、为什么停、下一步做什么”。
4. **自动化最大化**：机器能发现、创建、读取、验证、恢复的事实全部自动完成；正常只把 OAuth/2FA/验证码/真实 secret/不可替代决策交给人。
5. **部署稳定性**：重复 install/setup/start/status/stop、失败后重入、外部状态漂移和恢复行为稳定、幂等、fail-closed、可诊断，不制造不完整副作用。
6. **职责边界**：各 Package/Module 自己拥有真实状态与 lifecycle；Platform CLI 只做发现、排序、输入桥接、调用、聚合和用户呈现，不维护第二套业务真值。

必须严格区分：

```text
DEPLOYMENT_SUCCESS != SYSTEM_REAL_USABLE
```

当前 **不要求** J0～J6 业务 Journey、真实协作/Approval/Effect、Browser/File 实际业务任务执行、手机 FAST/THINK 联合执行等后续能力成立；这些属于后续 Real 阶段。只要部署合同本身成立，就应结束当前部署阶段并向后推进，禁止继续拿“系统是否真实完成业务任务”卡住部署。

## 2. 当前冻结的 Owner / Product 边界

每个 Module 对自己的真值负责：

```text
Module
├─ status()：真实观察自己的 setup/runtime 状态
├─ setup()：执行自己拥有的配置与恢复
├─ start()/stop()：拥有自己的生命周期
├─ 真实探测与证据有效性判断
├─ 状态/失败持久化
├─ 恢复建议
└─ READY / ACTION_REQUIRED / BLOCKED / FAILED 真值
```

Platform 只负责：

```text
调用 Module
→ 依赖/产品顺序编排
→ 收集用户输入并结构化传给 Module
→ 聚合 Module status
→ 找当前唯一根动作
→ 收敛普通用户输出
→ 做通用合同一致性保护
```

**禁止 Platform 替 Module 猜状态、补状态、伪造 READY、覆盖真实 FAILED，或实现 Module 专属业务真值。**

用户正式产品入口固定为：`platform install → platform setup → platform start`。普通用户不应执行 package-level `pnpm exec`、理解内部 moduleRef、Tunnel ID/port/shared facts 或模型内部字段。

### 9.1 效率规则

- **脚本优先**：重复、机械、确定的动作（workspace clean、Registry readback、状态采集、CLI 状态机、hygiene check）优先沉淀为安全脚本/harness，不反复用几十次 MCP 调用模拟手工。

- **发布按整改批次，不按单 Bug**：一轮发现 → 一轮整改 → 一轮验证 → 一次版本/发布 → Fresh replay，避免 Registry 变成逐 Bug 日志。
