# 执行纪律与工具规则

## 1. 验收阶段三方分工

### 验证总纲总控（默认由当前主 Chat 承担）

负责：阶段状态、验收目标、PASS/FAIL 条件、最短真实 Journey、failure 分类、root owner、整改边界、Evidence 审查、STOP/GO 与是否允许进入下一 Real。

总控的默认身份是 **验收主持者**，不是持续开发者。发现失败时先分类和裁决；需要工程整改时，优先把已经锁定的最小整改任务交给 Codex / 领域执行者。只有用户明确要求总控直接修复时，才由总控进入代码修改。

**当前 Deployment Closeout 是明确例外。** 用户已在 `09` 中授予主 Chat 持续执行权限：下一主 Chat 可以在已冻结 Deployment 范围内自行完成真实测试、Root Cause 定位、批量源码整改、统一验证、真实发包、清理真实产品工作区并继续 Fresh replay，直到 `DEPLOYMENT_SUCCESS=YES` 或上下文极限；不需要把每个 Deployment Bug 再转交 Codex 或逐项申请。该例外不扩展到 Frozen Contract Change、git push、远端 Tunnel 删除或部署后的业务系统可用性测试。

### Codex / 领域执行者

负责：按总控冻结的范围执行验证或整改、收集 evidence、CodeGraph 定位、实现最小 fix、跑 targeted regression、返回可复核结果。

执行者无权自行扩大验收范围、重开已 PASS 阶段、修改 Frozen Architecture/Owner/Contract，或仅凭测试全绿宣布 Real PASS。

### 用户

只承担真正不可替代的人类/外部动作与必要授权，例如账号本人 OAuth/登录确认、2FA、验证码、真实 secret 输入、明确的 Allow/Deny 决策、手机模型必须前台完成的动作、发布授权等。

普通 CLI 交互、Chrome 页面操作、Extension 验证、页面截图/状态读取、Console/Network 检查、浏览器内可自动完成的点击与表单输入，默认由 ChatGPT 通过 Local Dev / Playwright Chrome 独立完成，不再机械转交用户。机器能够自动确定或 producer-owned 的事实不得反问用户。

## 2. 验收默认先只读，整改必须过门

真实失败出现后先按 `04-测试验证与验收方法.md` 分类。

- A / B：继续完成真实前置，不进入代码整改。
- C / D：总控锁定 root owner、允许文件/Package 范围、回归测试 seam、原场景重放要求后，才允许工程修改。
- E：立即 STOP，进入正式 Spec/Contract/Design Change，不允许执行者自行补设计。

不得采用“看到错误 → 先改代码 → 再解释为什么”的顺序。

### 2.1 授权边界硬门：发现问题不等于获得修复授权

用户当前明确任务与阶段边界优先于总控自己的工程判断。执行过程中发现新的 residual、异常现象、潜在缺陷或合同疑点时，若它不在当前已授权整改范围内，固定执行：`记录事实 → 判断是否影响当前目标 → 向用户汇报 → STOP 等待裁决`。禁止因为“看起来值得修”“可能影响质量”就自动进入 CodeGraph 深挖、源码修改、补测试、重新 version / pack / install / release。

主动承担 Stop/Go、根因判断和质量控制，不等于可以扩大授权范围。`DISCOVER / REPORT / EXECUTE` 必须分离：发现和报告可以主动进行；修改、发布、迁移和重新验收只能发生在原任务已明确包含或用户再次明确授权的范围内。

用户已经明确“发布完成后交给我人工测试”“到这里停止”“等待我测试”等阶段切换时，该阶段边界视为 `HARD STOP`。发布后的必要核验可以完成，但发现新的非当前 blocker 时只记录并汇报，不得自行重开整改循环。

若用户出现“停”“不对”“你在干什么”“为什么又做了”“？”等明确质疑当前执行方向的信号，立即进入 `IMMEDIATE_EXECUTION_FREEZE`：停止一切推进型工具调用，只允许恢复权威状态和解释已发生事实；在重新获得明确授权前，不继续分析扩展、修改、测试、发布或安装。

### 2.2 2026-08-29 Fresh Workspace 人工验收后的最高执行规则

当前新增硬规则：`ISSUE_DISCOVERY != FIX_AUTHORIZATION`。用户已明确要求“**有问题先列出来，再去查；查清后先记录，不要直接做**”。因此在真实人工验收、恢复现场和后续整改中固定执行：

```text
列出问题
→ 只读查根因
→ 记录 evidence / 影响 / 建议
→ STOP 等用户授权
→ 才允许整改
```

当前真实 Workspace / runtime / 远端资源现场本身是证据。未经用户授权，禁止删除远端 orphan Dev Tunnel、reset/clean 当前 dirty source working tree、盲目重跑会创建远端资源的 dev-tunnel setup。下一 Chat 的当前唯一执行入口固定为 `09-Real3当前上下文与未解决问题-20260829.md`。

产品层新增总原则：**Platform CLI 必须成为唯一、专业、低心智负担的用户入口。** 正常 onboarding 不应让用户理解或执行内部 Module/package CLI、package-level `pnpm exec`、package manager 切换、FAST/REASON 单模型 URL、Tunnel ownership/port/shared facts 等实现细节。

`platform setup` 的目标交互固定为：一次只处理一个当前最前置 root prerequisite；机器可做的全部自动完成；遇第一个不可约人类动作或失败时只展示一个清晰步骤并 STOP；动作完成后自动观察 READY，再进入下一项。禁止同时拉起多个浏览器/人工流程。

## 3. 收官整改默认不做 checkpoint

当前收官/交叉审计阶段默认 **不再按 2～4 文件或 5 文件硬门制造 checkpoint ZIP**。Git working tree 本身作为连续整改状态；除非用户明确要求保全包、需要跨环境转移，或即将执行高风险/不可逆操作，否则不创建 checkpoint。

禁止为了 checkpoint 人为拆小一个完整 root cause。一个 root cause 涉及多少必要文件，就一次性完成其最小闭环；同时禁止 `reset / checkout / clean` 等破坏当前 working tree 的动作。

## 4. ChatGPT 本机工具链、自动化测试与提效规则

### 4.1 `gptweb-mcp` 是统一生命周期入口

ChatGPT 使用本机工程能力时，统一通过：

```text
/Users/agent/.local/bin/gptweb-mcp
```

当前统一托管三个核心 MCP Runtime：

```text
local-dev
codegraph
playwright-chrome
```

LaunchAgent：

```text
/Users/agent/Library/LaunchAgents/com.sayhello.gptweb-mcp.plist
```

每 60 秒执行一次 `gptweb-mcp start` 做自动恢复。日常只使用统一入口：

```text
gptweb-mcp start
gptweb-mcp status
gptweb-mcp test
gptweb-mcp stop
gptweb-mcp restart
```

`gptweb-mcp test` 的正常目标是 `GPTWEB_MCP=3/3_READY`。单项异常时先查对应 `tunnel-client runtimes status <alias> --json`，不要先重装插件、重建 Tunnel 或重启全部环境。Tunnel ID、runtime command、profile 等易变化细节以 `gptweb-mcp` 和 `~/.config/tunnel-client/` 当前配置为真源，不在公共上下文复制第二份配置。

Playwright Chrome 当前通过 `/Users/agent/.config/openai/tunnel-client/playwright-chrome-mcp.sh` 接入真实 Chrome，使用 Playwright MCP extension 模式；它不是 Chrome for Testing 专用链路，也不应默认要求重启用户真实 Chrome。

### 4.2 三个 MCP 的职责边界

**CodeGraph = 代码结构真相 / 仓库关系地图。** 仓库级结构问题默认第一入口，用于 symbol、caller/callee、runtime composition、factory/provider/service/adapter 链、模块依赖、注册关系、ownership boundary、blast radius。它负责回答“代码理论上如何连接、一个改动会影响哪里”，不负责当前磁盘写操作、进程或浏览器 reality。

**Local Dev = 本机实现与运行真相 / 本机执行层。** 用于读取和批量修改当前真实文件、执行 shell、Git、进程、日志、package manager、test/typecheck/build/gate、runtime/evidence/安装物检查。dirty working tree 下当前源码、Git diff 和实际进程优先于缓存或历史索引；若 CodeGraph 与当前源码冲突，只把相关 graph 结果视为 stale，不因此放弃整个结构分析。

**Playwright Chrome = 浏览器真相 / ChatGPT 的眼睛和浏览器里的手。** 它不仅用于点网页，而是 ChatGPT 独立完成真实浏览器自动化和 E2E 验收的核心感知能力：读取 tabs、URL、页面结构和可见状态，点击/输入，截图，检查 Console/Network，观察 Extension、登录态、授权页、真实 Web UI 和交互后状态。只看 CLI/evidence 不能替代 Playwright Chrome 对“用户眼前实际上发生了什么”的验证。

### 4.3 默认组合路径

仓库级工程问题固定优先：

```text
CodeGraph 定位结构 / blast radius
→ Local Dev 读取当前源码验证关键节点
→ Local Dev 精确搜索反查 import / registration / bypass
→ 批量完成已授权修改
→ 一次性 targeted/full tests + gate
→ 若涉及 Web/Extension，再用 Playwright Chrome 重放真实场景
```

真实 E2E / 人工验收自动化固定优先：

```text
Local Dev 建立真实 Workspace / CLI / process 前置
→ Playwright Chrome 观察并操作真实浏览器
→ Local Dev 回读 Module status / evidence / filesystem / process
→ Playwright Chrome 再确认用户可见结果
→ 三方证据一致后才判 PASS
```

必须区分“内部状态文件存在”和“浏览器当前真的可用”。例如 Browser Extension 的 READY 不能只凭旧 `verification.json`；需要在必要时通过 Playwright Chrome 观察真实扩展/UI/页面行为，并与 Module status、heartbeat/evidence freshness 交叉验证。

### 4.4 默认自动化边界

普通 CLI 交互（Enter、Yes/No、文本输入、菜单、错误输入、取消、重试）默认由 ChatGPT 通过 Local Dev 的交互进程/PTY 自动完成。浏览器中的普通点击、表单、截图、页面检查、Extension 验证默认由 Playwright Chrome 完成。只有账号本人授权、2FA、验证码、真实 secret、不可替代的人工决策或外部系统明确要求本人动作时才暂停并叫用户；授权完成后立即恢复自动接管。

### 4.5 批量执行优先，减少 Chat 往返

默认目标不是“每次调用只做一个小动作”，而是在边界清楚后一次完成一个完整机械批次：

- 同一 root cause 涉及多个文件时，先确定完整文件集合，再一次性修改，不逐文件来回确认；
- 同构机械变更优先用脚本/codemod/精确批量替换，先抽样验证 1～2 个文件，再批量应用，再统一 diff；
- 多个互不依赖的只读检查可以一次命令/一次 harness 并行采集；
- 状态机测试优先写临时 harness，一次执行多命令并自动记录 exit/stdout/stderr/Git/evidence/process，而不是让用户逐条复制粘贴；
- format/lint/test/build/governance 默认在一个整改批次末统一执行，禁止每改一个文件就跑一轮全套验证；
- 长任务启动一次后按合理间隔读取进度，禁止高频 poll；
- install/publish/deploy/migration/Tunnel provisioning 等非幂等操作若 timeout/UNKNOWN，先恢复权威状态，绝不盲重试。

**跨文档同步也属于批量任务。** 同一个事实/规则需要同步到 `05 / 09 / 10 / README` 等多个上下文文件时，固定执行：`一次批量检索全部目标 → 先形成变更矩阵（事实/目标文件/落点）→ 一次脚本或批量 edit 完成全部修改 → 一次统一 diff/check`。禁止按“读 05 → 改 05 → 读 09 → 改 09 → 读 10 → 改 10”的串行往返。

**确定性文档更新禁止逐文件验证。** 如果修改只是同一已确认事实的镜像同步，不得每改一个文件就重新 read/search；只在批量修改完成后统一做冲突扫描、`git diff --check` 和精确 diff 复核。只有某个文件结构与预期不一致时，才单独降级处理该文件。

**实时反馈按“验收/整改步骤”而不是按“文档文件数”计数。** 一次跨 3～5 个文档的同步更新算一个有意义步骤；不得为了满足实时反馈把本可批量完成的动作人为拆成十几次工具调用和十几条反馈。

批量优先不等于扩大授权。`ISSUE_DISCOVERY != FIX_AUTHORIZATION` 仍然有效；只有已经冻结并获授权的整改范围才允许批量处理。

### 4.6 真实测试方法要持续回写和调优

`05` 是跨 Chat 的长期执行方法真源之一。后续真实测试只要形成可复用的方法改进，就应及时回写这里，而不是只留在某个 Chat：例如更可靠的 CLI PTY 驱动方式、Playwright Chrome 自动化路径、Browser/CLI/evidence 三方交叉验证、批量编辑脚本、批量状态机 harness、长任务恢复策略、MCP 故障诊断与恢复办法。

只沉淀稳定方法和提效规则，不保存单次测试流水账、临时 PID、一次性截图或短期 blocker；这些仍放当前 `09` / evidence / issue log。

### 4.7 重复机械动作默认脚本化

同一个真实验收循环里重复出现两次以上、输入/输出边界稳定且可以加安全门的机械动作，默认优先脚本/harness 化，而不是继续用 Chat + MCP 一步一步模拟人工。例如：真实 Workspace 清理、Registry exact preflight/readback、CLI 状态机执行、workspace hygiene、Module/evidence/process 批量采集、重复 lifecycle 调用。

脚本必须 fail-closed：先校验目标目录/环境/允许删除集合，再 mutation；不得为了“自动化”放宽远端资源删除、源码 `reset/clean`、secret 输出、publish UNKNOWN 重试等安全边界。

### 4.8 避免 Chat 长任务卡死

自动化目标是“连续完成更多工作”，不是“单次工具调用无限长”。**“不要做长任务”只约束单次工具调用 / 单个不可恢复任务，不限制整个 Chat 的连续执行时长。不存在 25 分钟、30 分钟或任何人为分钟数到了就主动停工的规则。**

正确执行方式是：把长流程拆成短而可恢复的批次，每批有明确输入、输出和落盘状态；一个短批次结束后立即进入下一个短批次，不因累计执行时长、自然阶段切换、局部 PASS 或“担心可能变成长任务”而主动结束回复。Chat 可以连续执行多个短批次，直到目标完成或出现真实 hard blocker。

长进程只启动一次并保存 PID，合理间隔读回。任何 install/publish/deploy/setup 等动作超时或 UNKNOWN 时，先恢复权威状态再决定下一步；**UNKNOWN 只要求恢复状态，不等于结束整个执行。**

**`Blocked=true`、后台进程长时间运行、暂时没有新 stdout/stderr、连续多次读回为 `(No output in requested range)`，都不构成 hard blocker。** 这些状态只说明“当前没有新的可见输出”或“进程仍在等待/运行”，不能据此推断系统强制截断、工具执行上限、上下文硬限制或必须结束 Chat。固定处理顺序是：`降低轮询频率 → 检查 session/PID/子进程/CPU/文件或外部权威状态 → 若仍在运行则继续等待 → 若状态 UNKNOWN 则恢复权威状态`；只在工具明确返回不可恢复错误或真实 hard limit 时才允许中断整个连续执行。

状态机/harness 可以一次覆盖多个场景，但自身也应支持分段、续跑和结果落盘，避免一条超长 shell pipeline 或一个巨大浏览器脚本成为单点卡死源。

允许中断整个连续执行的条件只来自真实事实：不可替代的人类授权/secret、Frozen Contract/Owner/Architecture 变更、工具明确不可恢复失败、上下文确有硬极限且必须安全交接，或最终 `DEPLOYMENT_SUCCESS=YES`。禁止凭“已经执行了很久”“大约二三十分钟”“这一段看起来结束了”等主观感觉自行停工。

### 4.8.1 目标保全硬规则：工具还能工作就必须继续

Deployment Closeout 的最高执行目标只有一个：**把当前真实 Deployment Journey 推进到 `DEPLOYMENT_SUCCESS=YES`。** 任何执行策略、风险控制、汇报习惯、阶段感、上下文焦虑都不得反过来破坏这个目标。

固定判定：

```text
工具仍可正常调用
+ 当前没有可证明的不可恢复 tool failure
+ 当前没有不可替代的人类动作
+ 当前不需要 Frozen Contract / Owner / Architecture 变更
+ DEPLOYMENT_SUCCESS != YES

=> 必须继续下一短批次
=> 禁止主动结束执行
=> 禁止把“可能快到限制”“工具调用很多”“上下文很长”“已经工作很久”当成停止依据
```

**风险预测不是 hard blocker。** 模型只能依据已经观察到的工具错误、真实上下文硬限制或明确的人类/架构门决定中断，不能根据主观预判提前收口。没有明确错误码、tool unavailable、不可恢复 timeout、context hard-limit 事实时，禁止声称“系统强制停止”“工具执行上限”“上下文限制导致必须停”。

如果一个短批次完成，固定动作只能是：`记录最小必要状态 → 立即进入下一短批次`。只有真正 hard blocker 才允许把下一步交给用户或下一 Chat。

## 4.9 2026-08-30 Deployment Closeout 执行偏差复盘与强制纠偏

本节来自 2026-08-30 Deployment Closeout 的实际执行失误，作为后续主 Chat / 执行者的长期硬规则。此次偏差不是工具能力不足，而是执行方法违背了本文件已经明确的提效纪律：用户前一晚已经要求“**减少 checkpoint，阶段末统一验证；不要修一个问题就跑一次全仓测试**”，但主 Chat 仍多次把局部整改升级成全仓 Gate，导致真实人工部署主线程被 CI/工程验证抢占，执行效率明显下降。

### 4.9.1 这次具体做错了什么

1. **把工程 Gate 当成主线程。** 正确主线程应始终是 `Fresh Workspace → install → status → setup → Browser Extension → Dev Tunnel → Model → start → status → recovery → PASS`；实际执行却多次变成“发现一个问题 → 修源码 → package test → typecheck → architecture → publishability → full check → 再回真实部署”，导致每个局部问题都把验收现场切回工程仓库内部。
2. **重复跑昂贵全仓验证。** `pnpm check`、全量 build/lint/typecheck/test/architecture/publishability 只能在整改批次末、release 前或阶段最终收口时统一执行；不得因为单个 Dev Tunnel、Execution Local、SETUP 文档或 Browser Extension 局部修复就重跑一整套全仓 Gate。
3. **没有持续维护唯一的真实验收状态表。** 历史 `PASS`、package tests PASS、Module.install PASS、安装物存在，都不能替代当前 Fresh Workspace 的真实外部状态。缺少这张主表直接导致 Browser Extension 被遗漏。
4. **Browser reality 没有始终作为一等真值。** Browser Extension 的真实验收必须持续用 Playwright Chrome 观察“用户眼前是否真的加载、启用、pairing、heartbeat live”；不能等 CLI/文件/测试都绿了最后才看浏览器。
5. **发布事务边界设计不完整。** 第一次 version bump 后未强制重新 build，导致 Registry tarball 中 package/proflow.module 已是新版本而 dist descriptor 仍是旧版本，Fresh install 才暴露 `DESCRIPTOR_INVALID`，白跑了一轮 version/publish/clean/install。此后 release transaction 必须把 `version → build → publishability → publish → Registry exact verify` 视为不可拆分链路。
6. **安全谨慎使用过度。** `publish / delete / migration / remote resource / destructive Git` 需要高强度验证；普通本地可恢复动作应批量、脚本化、连续执行。不得把“避免犯错”执行成“每一步都做最大强度验证”。

### 4.9.2 全仓 Gate 的强制频率规则

后续固定采用三级验证，不得自行升级：

```text
局部修复
→ targeted test / 精确 reverse verify
→ affected package test + typecheck（仅必要时）
→ 立即回真实验收主线程

一个整改批次结束
→ affected packages 统一验证
→ changed-files biome / git diff --check
→ 继续真实场景重放

阶段收口 / release 前
→ pnpm check 全仓 Gate 只跑一次
→ build / architecture / publishability / release sync
```

若局部修复后 targeted/package 验证已经证明 root cause 关闭，**禁止为了“更放心”立刻再跑全仓 `pnpm check`**。只有以下情况允许提前升级：修改了公共 Contract / build/release machinery / 多 Package 公共基础设施，或 targeted evidence 无法判断 blast radius。

发布完成后如果没有新的源码修改，默认也禁止再次重跑全仓 source Gate；直接做 Registry exact readback 和真实 Fresh replay。Fresh replay 新发现源码 root cause 时，才回到对应 targeted 修复循环。

### 4.9.3 真实人工部署必须拥有唯一主状态表

Deployment Closeout 期间必须始终维护并以它为最高真值：

```text
Registry exact artifacts
Fresh workspace
platform bootstrap
platform install 23/23
Browser Extension real load
Browser pairing / live heartbeat
Dev Tunnel real setup
Model Provider / FAST / THINK real setup
platform start
final platform status
failure recovery
repeat / idempotency
DEPLOYMENT_SUCCESS
```

任何 package test、typecheck、historical Real-1 PASS、Module.install PASS、`.proflow` 文件存在，都**不得**把外部 reality 项改成 PASS。

尤其 Browser Extension 只有满足：

```text
真实 Chrome 中可见
→ enabled
→ extension runtime 活着
→ pairing 完成
→ live heartbeat 成立
→ platform status 读取真实 READY
```

才允许 `Browser Extension = PASS`。

Fresh cleanup 一旦删除 `.proflow` / pairing evidence / runtime state，就必须自动把 Browser Extension、Dev Tunnel、Model 等相关 Fresh reality 项重新置为 `NO / NEEDS_REVALIDATION`；禁止引用历史 PASS 继承当前 Fresh Workspace 结论。这是本次“忘掉 Browser Extension”的直接纠偏规则。

**智能体创建是 Deployment 最终 PASS 的必要 Gate。** Real-2 历史上对 Custom GPT / Worker Identity 的真实 PASS 只能证明能力曾经成立，不能替代当前 Fresh Registry Deployment 的真实创建验收。最终 Deployment 必须至少通过当前 Fresh 安装物真实创建冻结要求的智能体，并交叉验证 ChatGPT 侧创建结果与 owner-local identity/config/evidence 回写一致。历史 Real-2 PASS 可用于减少无意义重复探索，但不得把当前 Deployment 的该 Gate 直接标 PASS。

**Fresh Browser 安装必须清除 Chrome 侧旧产品 registration。** 如果真实 Chrome 里仍保留上一轮同一 unpacked 路径注册的产品扩展，即使当前 Fresh Workspace 已经把目录内容更新为新版本，也不得通过 `Reload` 把它当作 Fresh install PASS。固定顺序是：`确认旧产品扩展身份/版本 → Remove/卸载旧产品扩展 → 确认旧 registration 消失 → 从当前 Fresh Workspace 的安装目录重新执行“加载未打包的扩展程序” → 再验证新版本 / enabled / Service Worker / pairing / live heartbeat / platform status`。`Reload` 只允许用于后续 runtime recovery / idempotency 测试，不得替代 Fresh install 证据。

类似地，所有 Fresh reality 验收都必须同时清理**产品外部持久状态**，不能只清理 Workspace 文件：浏览器扩展要考虑 Chrome registration；Tunnel 要区分可复用的远端 owned resource 与本地 runtime state；模型要清理 owner-local binding/evidence 后重新 probe。判断 Fresh 的原则是“旧状态不能让新链路自动 PASS”，而不是机械删除一切远端资源。

**Chrome 内部页与 macOS/Chrome 原生弹窗必须按系统 UI 处理。** `chrome://extensions`、扩展删除确认框、Load unpacked 的目录选择器等不属于普通 Web DOM；Playwright 对这些区域不可作为唯一执行手段。固定路径是：先用真实 Chrome/截图确认当前页面 → 用 macOS Accessibility(AX) 定位按钮/窗口的实时 position/size → 必要时用系统级鼠标/键盘事件完成点击、确认、路径输入 → 操作后同时用 AX 树和截图确认真实结果。禁止仅因原生弹窗“消失”就判动作成功；例如删除扩展必须继续确认产品卡片/heading 与 registration 实际消失。

#### macOS Chrome 扩展卸载的稳定系统级路径

`chrome://extensions` 的产品卡片可由 Chrome AX（Accessibility）树观察；点击卡片“移除”后出现的 `要删除“<扩展名>”吗？` 确认框属于 Chrome/macOS 原生可访问 UI，不应按普通网页 DOM 处理。稳定自动化固定为：`激活 Google Chrome → AX 按扩展 heading 定位产品卡片 → AX 读取同卡片“移除”按钮 bounds → macOS CGEvent 真实鼠标点击按钮中心 → AX 定位标题包含目标扩展名的确认 AXWindow → AX 读取确认“移除”按钮 bounds → 在 Chrome 保持前台的同一原子进程内用 CGEvent 点击确认 → AX + 截图双重确认产品 heading/确认窗均消失`。

禁止写死某次截图坐标；坐标只允许来自当前 AX bounds。还要防止 ChatGPT/Terminal 抢前台：`activate Chrome → locate → click → verify` 必须尽量在同一原子系统脚本里完成。确认浮层在 Chrome 失焦时可能自动消失，因此“先定位后跨多个工具调用点击”不可靠。该路径已经在 2026-08-30 Fresh Browser replay 中真实证明可用。

### 4.9.4 真实验收主线程不得被 CI 抢占

当前 Deployment Closeout 的职责是**模拟真实用户连续部署并闭环问题**，不是充当持续 CI 总控。正确节奏固定为：

```text
真实 Journey 向前推进
→ 遇到 blocker
→ 定位 root cause
→ 最小修改
→ targeted/package regression
→ 立刻回原 Journey 重放
→ 累积到批次末再统一 full gate
```

Playwright Chrome、Local Dev CLI、filesystem/evidence/process 必须伴随 Journey 同步观察；不能先在仓库内部连续做很久，再回浏览器看现实。用户肉眼可见的部署结果优先级高于“测试套件看起来很绿”。

### 4.9.5 执行效率硬约束

- **已经真实成功过的人机操作禁止再次临场探索。** 执行前必须先检索仓库当前 SOP / 历史 evidence / 已有 harness；若已经存在成功路径，直接复用，除非当前现实证据证明该路径失效。不得因为换了 Fresh Workspace、版本或 Chat 就重新试坐标、重新猜工具边界；
- **描述性文档不等于执行沉淀。** 对 Chrome/macOS 原生 UI、Fresh 清理、Registry readback、lifecycle recovery 等重复机械动作，第一次成功后必须记录最短成功路径；第二次出现即升级为仓库脚本/harness，固定输入、动作、成功判据和失败恢复。禁止只留下“用户应该怎么点”的文字说明，却让总控下次重新发明自动化；
- **模拟真人验收不等于手工逐原语执行。** 验收必须走用户真实产品入口和真实 UI/CLI，但已证明稳定的鼠标/键盘/PTY 交互允许且应当由 harness 原子化完成。目标是复现“真人会经历的路径与结果”，不是每次重新研究如何点按钮；
- **交互驱动失败一次就切方法，不在坏 transport 上反复试。** CLI prompt 若普通 `interact_with_process`/PTY 文本注入一次不能可靠提交，立即保存现场并切换到 `expect`/pexpect 或已有交互 harness，通过 prompt pattern → input → outcome 驱动；禁止连续多次向同一个失效 prompt 盲发文本/Enter；
- 相同真实验收循环中重复两次以上的清理、Registry readback、status 采集、lifecycle 重放，立即脚本/harness 化；Browser Extension 的 remove / load-unpacked / verify 也属于此规则；
- **状态采集采用白名单，不递归 dump secrets。** 读取 `.proflow/runtime`、Module state 或 evidence 时只列/读明确允许的状态文件；禁止 `find ... -type f | cat/sed` 这类可能扫到 `secrets/`、token、credential 的宽泛命令。发现敏感文件路径时只记录存在性/权限，不读取内容；
- 多个独立只读检查一次批量执行，不拆成多轮 Chat 往返；
- 长进程一次启动，合理间隔读取，避免碎片化高频 poll；
- 不因汇报进度触发 format/test/checkpoint；
- 不因为一个局部 PASS、自然阶段切换、累计执行时间较长或“担心可能成为长任务”就停下来做总结；Deployment Closeout 只有**已被工具/上下文事实明确证明**的 hard blocker、必须安全交接的真实上下文硬极限，或 `DEPLOYMENT_SUCCESS=YES` 才允许中断连续执行；禁止主观估计上下文快到极限后自行停工；
- 后续若再次出现“修一个问题就跑一次全仓测试”，视为违反本文件执行纪律，而不是保守策略。

## 5. 先审完、冻结 residual list、再一次整改

交叉审计和收官整改禁止“发现一个 → 立刻修一个 → 再继续审”的循环。固定顺序：

```text
冻结审计范围
→ 一次性完成全部只读审计
→ 汇总并冻结完整 residual / root-cause list
→ 一次性整改已确认 residual
→ pnpm format（一次）
→ changed-files scoped biome check --write（一次）
→ affected-package targeted/full tests
→ governance / surface regenerate + check（仅在受影响时）
→ typecheck / build / architecture / publishability / git diff --check
→ 精确 reverse verify
→ 原真实验收场景重放
```

默认 **不做中间 format、不做中间 test、不做中间 governance、不因实时汇报触发验证**。只有出现可能破坏已有真值、无法继续静态判断或需要立即确定 STOP/GO 的高风险情况，才允许提前跑最小验证。

若 residual list 冻结后，在整改/验证阶段又出现一个完全不同的新 root cause，立即 STOP 并重新评估审计方法是否失效，不继续“下饺子式”顺手修复。

结构 gate 证明实现质量；原场景重放证明验收 blocker 是否真正关闭，两者不能互相替代。

## 6. 实时汇报纪律

**2026-08-30 起，Deployment Closeout 强制逐步实时反馈。** 用户要求 ChatGPT 以“模拟真实人进行测试验收”的方式执行：每完成一个有意义的测试/操作步骤，都必须立即用一条简短消息反馈“刚做了什么、真实结果是什么、下一步做什么”。不得连续执行多个用户可感知步骤后才一次性总结，也不得让用户通过截图/终端自行猜当前进度。

实时反馈不是审批门，也不是停工点。固定节奏是：`执行一个有意义步骤 → 立即反馈结果 → 不等待用户确认 → 继续下一步骤`。只有用户明确要求暂停/纠偏，或出现真实 hard blocker，才停止继续。反馈本身不得触发 checkpoint、format、test、full gate 或其它额外验证。

“一个有意义步骤”按验收动作划分，而不是按每个底层 tool call 划分。例如：卸载旧扩展、Fresh 加载新扩展、pairing 成功、Tunnel setup READY、Provider inventory probe、FAST/THINK 映射、platform start、recovery 场景，各自完成后立即反馈；同一步内部为恢复状态而做的多次只读 tool call 可合并为一次结果反馈。

推荐格式：`[步骤] 刚完成：<动作>｜结果：PASS/FAIL/DOING + 关键事实｜下一步：<动作>`。长进程启动后先反馈“已启动 + PID/目标”，之后只在状态发生变化、发现 blocker 或完成时反馈，禁止高频无信息轮询式刷屏。

## 7. 发布纪律

发布前先确认 branch / HEAD / working tree / release status；长 publish 状态 UNKNOWN 时先恢复权威状态，禁止重复发布。

总控负责决定“是否已经 READY_FOR_REPUBLISH”；实际 version/publish 必须遵守用户授权与 release policy。`git push` 与 `npm publish` 是两个独立授权边界，用户授权真实发包不自动授权 push。

真实 npm Registry 发布固定使用 Granular Access Token，不通过删除 WebAuthn/2FA 来消除交互验证。当前已核验本机存在 token `proflow-local-publish`，且 `bypass2fa=true`；只允许记录 token 名称和策略，禁止读取、输出或提交 secret。发布凭据优先放在当前 shell 环境变量和 `0600` 临时 npmrc，发布结束立即清理。

正式 publish 固定采用：`Registry exact preflight → 只保留 MISSING package@version → pnpm -r publish --access public 一次递归发布 → 一次并发 Registry exact verify`。默认禁止逐 package 启动独立 WebAuthn publish 循环；也禁止 `--force` 重发 Registry 已存在版本。若 publish 中断、超时或返回 UNKNOWN，先全量 exact readback，再决定是否继续。

Fresh Registry 最终证明必须使用真正新的 Workspace / cache，不能拿旧安装物、local link、repo source 或 tarball 冒充 Registry reality。做真实 Fresh Workspace 安装验收前，产品根工作区应清除 `.proflow/`、`node_modules/`、安装生成的 `package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml` 以及本地 `releases/`；源码 `repos/` 与 Git/README 等非安装资产保留。真实 Registry 验收时禁止重新引入本地 tarball override。
