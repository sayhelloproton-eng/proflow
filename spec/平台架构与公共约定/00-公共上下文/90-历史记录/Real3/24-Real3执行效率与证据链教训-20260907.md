# Real-3｜执行效率与证据链教训｜2026-09-07

> 性质：本轮 Real-3 SAME-SCENE 后半段事故复盘。事故细节留在这里；可复用规则已回写长期规则与自动化 Runbook。
> 边界：本文不替代 `02-当前接力/CURRENT.md`，也不把当前尚未完成的 Real-3 写成 PASS。

## 1. 为什么这轮明明有 Codex，后半段仍然明显变慢

Codex 在 D1 这类**范围已冻结、设计已明确、可以批量实现**的任务上确实显著提速：实现、回归、typecheck、governance、release candidate 可以一次完成。

但 SAME-SCENE 后半段进入的是：

```text
真实 Task durable state
→ Observer / worker.wake
→ Chrome MV3 Service Worker
→ Browser actual adoption
→ Registry / Workspace
→ 原 Conversation
```

这里瓶颈不再是“写代码速度”，而是**真实世界根因证明与证据链是否可信**。执行器可以加速已冻结修复，不能代替 Browser / Owner / Registry authority。

## 2. 本轮真正暴露的系统缺口

先后确认了三个真实问题：

1. `TASK_RESUMED` 已进入 Task Observer，但下层 `worker.wake` trigger allowlist 漏掉它，产生 `WAKE_TRIGGER_TYPE_INVALID / NOT_APPLIED`。
2. Extension startup attention reconstruction 存在无界 `sendMessage` 等待，理论上可阻塞后续 Observer recovery；该缺陷已补 bounded recovery regression。
3. 最关键：Chrome 实际仍注册旧 Extension Service Worker，而 verification 却写出了新 package version，形成 Browser adoption 假阳性。

## 3. 最大效率损失：把假的 adoption PASS 当成前提

当时的错误推理是：

```text
Workspace / materialized = 新版本
verification.moduleVersion = 新版本
PAIRING_HEARTBEAT = PASS
→ 推导 Chrome actual adoption = PASS
```

后来从 Chrome 自身 reality 读到：

```text
loaded path = 正确 materialized 目录
磁盘 manifest = 新版本
Chrome registered Service Worker = 旧版本
chrome://extensions 可见版本 = 旧版本
```

也就是说，我们随后一段“为什么新版本 startup recovery 没执行”的排障，实际上是在**旧 runtime 上分析新代码**。

根因是 pairing heartbeat 协议当时没有 browser-reported `moduleVersion`，deployment adapter 却用 `descriptor.moduleVersion` 写 verification。这个 durable evidence 只能证明 package 期望版本，不能证明 Browser runtime 真实版本。

这是本轮最高成本的误判。

## 4. 第二类效率损失：过早把真实 defect 锁成当前唯一 root cause

`rebuildCarrierAttentionsFromTabs()` 的无界等待是真缺陷，也值得修；但在 Chrome actual version 尚未被证明时，就把它升级为当前现场唯一 root cause 并完成一次 patch release，准入门过低。

永久结论：

```text
VALID_DEFECT != CURRENT_ROOT_CAUSE
```

Hotfix 发布前必须至少同时成立：

```text
CURRENT_RUNTIME_VERSION_PROVEN
FIRST_DIVERGENCE_PROVEN
OWNING_CODE_PATH_PROVEN
CAUSAL_REGRESSION_PROVEN
POST_RELEASE_AUTHORITY_DEFINED
```

否则只登记 defect，不进入当前 SAME-SCENE 主线 release。

## 5. 第三类效率损失：Browser 自动化路径重新发明

本轮曾出现：canonical helper 未达到预期后，又尝试临时 Swift AX、不同 selector、privileged navigation 等路线。部分脚本甚至只产生编译/参数错误，没有提供任何新的 Browser authority。

永久规则：

```text
已有 canonical helper
→ one canonical mutation
→ fresh visual/runtime readback
→ 若不符合预期，回 authority
→ 不通过“再换一种 UI 技术”继续试探
```

Playwright 负责普通 Web；仓库 Chrome helper / AX + screenshot 负责 privileged UI。除非现有 helper 本身被机械证明失效并进入独立修复，否则不得现场创造第三套控制链。

## 6. 第四类效率损失：Release Harness 形状错误

本轮出现过：包自身无 `build` script、`build-packages.mjs` 多传 `--`、zsh 多路径变量展开错误、`pnpm change status` 长时间不返回。

这些属于 Harness failure，不是产品 failure。未来固定：先从根 `package.json` 读取 canonical script；plan CLI 卡死时读取 changeset ledger/pending intent；runner 无退出回执时先查 OS process/产物，不盲重跑昂贵 gate。

## 7. Codex 的正确使用边界

Codex 本轮不是“失效”，而是适用边界被混淆。最有效的分工冻结为：

```text
总控
→ 真实现场观察
→ root cause / blast radius / acceptance 冻结

Codex / 领域执行器
→ 批量实现
→ targeted/full/typecheck/governance
→ release candidate

总控
→ Registry exact
→ Workspace adoption
→ Browser/runtime actual adoption
→ SAME-SCENE final acceptance
```

如果问题还处于“哪个 reality 才是真的”阶段，把它交给执行器不会自动变快；只会更快地产生未经证明的 patch。

## 8. 本轮永久落地的五条硬门

1. **Browser actual adoption 五联证据**：package/workspace、materialized manifest、Chrome 可见版本+ID、registered SW/browser-reported runtime version、verification version 全部一致。
2. **Hotfix Admission**：`VALID_DEFECT != CURRENT_ROOT_CAUSE`；没有 causal chain 不发布。
3. **FIRST_DIVERGENCE only**：第一层不一致时禁止继续向后层排障。
4. **Canonical helper only**：稳定 Browser helper 已存在时，不因一次失败现场发明替代 UI 技术路线。
5. **Harness failure 独立分类**：命令形状、runner、session、plan CLI 异常先修 Harness，不污染产品判断。

## 11. Patch Train 止损规则

以后阶段必须显式拆开：

```text
Integration Hardening
→ Failure Matrix / causal proof
→ Frozen Release Candidate
→ Final Real Gate
```

Final Real Gate 中再次出现新的阻塞性架构/生命周期缺口时，立即退出验收态，标记 `PAUSED_FOR_INTEGRATION_HARDENING`；不得继续用 `0.x.N → 0.x.N+1 → ...` 连续 patch 冒充最终验收。

当前 0.1.49 已触发该止损：production bridge reconnect 成功但 Observer 没有首个可见 recovery event，且 root cause 尚未证明。因此 `0.1.50=NOT_ADMITTED`，必须先区分 rearm callback、single-flight pending 与 collaboration recovery 三个候选。

## 12. 对 Codex 提速的最终认识

Codex 的价值是压缩**已冻结执行批次**，不是替代总控做 root-cause admission。正确优化目标从“让每个 patch 更快”改为“减少 patch loop 数量”：

```text
总控一次证明 FIRST_DIVERGENCE
→ 同 ownership domain 相邻 failure matrix 一次审完
→ Codex 一次实现/验证/release
→ 总控一次真实 adoption + SAME-SCENE
```

这比继续提高单个 release loop 的速度更重要。
