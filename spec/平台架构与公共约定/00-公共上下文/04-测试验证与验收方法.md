# 测试验证与最终验收方法

## 1. 当前方法定位

Phase 3 早期使用全量交叉审计，适合架构与实现尚未收口阶段。`READY_FOR_SMOKE = YES` 之后，当前主任务已经变为 **最终真实验收**。

这里定义的是 Real-1～Real-6 的 operational acceptance 方法，不替代 `06-测试计划` 中已冻结的 Unit → Domain → Contract → Integration → Real E2E → Fault/Recovery → Evidence 正式测试层级。

当前默认原则是：已有结构性证明只作为前置证据，最终阶段优先证明 Mock/静态门无法证明的真实外部行为、真实 owner state、真实 effect/result/evidence。

## 2. 每个 Real 的固定验收闭环

```text
确认上一 Real 已 PASS
→ 读取当前 Frozen contract / test plan
→ 定义本 Real 验收对象、PASS/FAIL、非目标
→ 选择最短真实 Journey
→ 执行并保存 evidence
→ 失败先分类
→ 必要时 CodeGraph / 源码定位 failure boundary
→ 最小整改
→ targeted regression
→ 原真实场景重放
→ 总控 STOP / GO
```

不得把“全仓测试全绿”当作真实 Journey PASS 的替代品，也不得因为单个真实失败就重新开启全仓历史审计。

## 3. 失败必须先分类，不能直接修

### A. Human / external action 未完成

例如真实登录/授权、Custom GPT 编辑、Chrome Extension 加载、手机模型前台操作。处理方式：引导最少必要人工动作，不判代码 blocker。

### B. 合法 producer prerequisite 尚未 READY

Consumer 缺少的是当前尚未完成的真实 producer fact。处理方式：先完成 producer，再重放；不得提前把 consumer 判成 bug。

### C. Machine-owned contract / shared-fact failure

机器本应自产或 producer 应提供的事实缺失、泄漏为用户配置、provider/consumer contract 不一致。处理方式：真实工程 blocker，进入最小 ownership/root-cause 定位。

### D. Implementation defect

Frozen contract 已明确，但实现行为不符合。处理方式：最小实现修复 + targeted regression + 原场景重放。

### E. Spec / Contract / External Behavior mismatch

真实 evidence 表明正确实现必须改变 Frozen Owner/State/Contract，或外部系统现实与冻结假设冲突。处理方式：`STOP → SPEC_GAP / CONTRACT_CONFLICT / EXTERNAL_BEHAVIOR_MISMATCH`；禁止执行者自行补设计。

只有 C / D 进入正常源码整改路径；A / B 继续验收前置，E 必须先做正式设计/合同决策。

## 4. Real 阶段验收顺序

- **Real-2**：三个 Agent Package → 真实 Custom GPT → Role register → durable identity → reload/reopen 后仍成立 → 至少一个真实 Gateway/Carrier identity probe。
- **Real-3**：重确认 J0 后直接跑 J1～J4；失败时才下钻 Task Store / Orchestration / Runtime。
- **Real-4**：真实 askPeer/replyPeer + Approval + Effect；必须有 owner durable state / real effect evidence，不以 API 200 代替。
- **Real-5**：按低噪音到高噪音逐步证明 File、Browser、FAST、REASON、调度与联合执行；真实 Chrome/Custom GPT/手机模型不能由 Mock 替代。
- **Real-6**：主动制造中断、重启、lost response、duplicate/UNKNOWN 等，验证 recovery/idempotency；最后完整重跑 J0～J6。

## 5. Deployment 系统端到端验收的固定主视角

**Deployment Closeout 的主测试身份固定为：模拟第一次使用 ProFlow 的普通用户，从真实产品入口进行系统端到端测试。** 这不是“开发者自测”，也不是“把 package tests / CLI exit code 跑绿”。

固定执行视角：

```text
前台：普通用户真实视角
→ 只使用公开产品入口和真实 UI / CLI
→ 不读取源码寻找下一步
→ 不执行内部 package CLI 救场
→ 不手改 .proflow / DB / shared facts / evidence 绕过产品路径
→ 不依赖 moduleRef、端口、Tunnel ID、owner 等内部知识完成部署

后台：验收总控真实校验
→ 用 Browser / CLI / runtime / filesystem / external reality 交叉确认系统真值

遇到失败：临时进入工程视角
→ 保存用户现场 → 定位 root cause → 最小修复 → targeted regression
→ 修完必须退出工程视角
→ 回到同一个普通用户端到端路径重放
```

只有当“不懂 ProFlow 内部架构的正常用户”能够沿公开入口完成部署，并且用户看到的 READY 与 Browser / Tunnel / Model / Agent / runtime 的真实状态一致，才允许继续判定 Deployment Product Acceptance。**任何依赖开发者内部知识才能绕过的成功，都不算用户端到端 PASS。**

## 6. Deployment Product Acceptance：技术可用之外的四个产品门

Deployment 的最终验收必须同时覆盖“技术真实可用”和“普通用户能低心智完成部署”。不能把 UX、自动化和 CLI 质量全部降级成上线后的可选 polish。

固定四个产品门：

1. **Cognitive Load / 用户心智门**：普通用户只理解产品级步骤和当前唯一动作；若必须理解 moduleRef、shared facts、内部端口、Tunnel ownership、provider inventory、credential file 等实现细节才能完成正常部署，则 FAIL。
2. **Automation / 自动化门**：机器可确定、producer-owned、可安全恢复的动作必须自动执行；若用户被要求重复输入机器已有事实、手动执行内部 package CLI、人工恢复本可自动恢复的资源，则 FAIL。
3. **CLI Interaction / 命令行交互门**：交互必须明确当前阶段、原因、所需动作、成功/失败和下一步；支持取消、重入、幂等和恢复。用户不应靠猜测或阅读内部日志才能继续。
4. **Default Output / 默认输出门**：正常输出只服务用户决策，固定聚焦 `当前状态 + 唯一 root cause + 下一步 + 最终结果`；内部 traversal、依赖图、owner 细节和诊断原文默认隐藏到 verbose/doctor/日志。

判定关系：

```text
技术主链真实跑通
= DEPLOYMENT_TECHNICAL_MAINLINE = PASS

技术主链 PASS
+ 用户心智门 PASS
+ 自动化门 PASS
+ CLI 交互门 PASS
+ 默认输出门 PASS
= DEPLOYMENT_SUCCESS = YES
```

非阻断的文案微调、视觉 polish 可以作为优化，不反向推翻已经成立的技术主链；但只要正常部署仍把内部复杂度甩给用户、存在明显可自动化却要求人工重复操作、交互无法明确指引下一步或默认输出具有误导性，就不能宣告完整 Deployment Product Acceptance。

## 7. PASS / Evidence 原则

`Business Fact`、`Evidence`、`Log` 必须分开。真实 PASS 至少要能回答：验收目标是什么、真实环境是什么、实际执行了什么、owner/external reality 是什么、是否有 fake/mock/bypass、为什么这些证据足以满足 Frozen contract。

以下均不能单独证明 REAL PASS：

- unit / contract / conformance 全绿；
- HTTP 200 或进程存活；
- CLI exit 0；
- README / schema 看起来正确；
- fake URL / fake provider / mock carrier；
- 手工修改 DB/内部 JSON 绕过正式路径。

修复完成后必须回到最初失败的真实场景重放；只有原场景从 FAIL 变为符合 Frozen contract，才算该 blocker 闭环。
