# 核心执行纪律与工具规则

> 性质：所有 Chat 默认必读的短版铁律。包/外部资源/流程细节必须路由到 `03-自动化知识库`，不要继续塞回本文。

## 1. 授权与裁决

- 用户是重大结构、Frozen Contract、Owner/State、范围扩张的裁决者。
- “整理 / 顺手优化 / 看起来更合理”不是修改授权。
- 已稳定、已 PASS、已 Frozen 的能力默认不重开；只有新的可复现 regression evidence 才允许局部修复。
- 修复局部问题时禁止借机大改稳定功能。

## 2. 最终真值

```text
正式 Spec / Frozen Contract = 应该是什么
当前 Git/source             = 当前实现事实
npm Registry                = 发布事实
Product Workspace           = 用户安装事实
真实 Browser/runtime        = 用户现实
```

源码/单测 PASS 只证明候选；真实发布包进入真实 Workspace 并重放原场景后，才证明修复有效。

## 3. 自动化必须模拟人工

自动化只能替代真人执行已有公开 CLI、真实 Browser/UI、真实恢复路径和等待/观察动作；不得为跑通测试直接写 `.proflow`、Owner DB、pairing evidence、node_modules 或远端资源状态。

## 4. 工具能力与路由顺序

本机工程工具按四个 Plane 分工，不把所有任务机械套成同一顺序：

```text
Repomix           = Context Plane    仓库级上下文打包、压缩、稳定 outputId、grep/read 按需检索
CodeGraph         = Structure Plane  symbol、caller/callee、依赖、composition、ownership、blast radius
Local Dev         = Execution Plane  当前磁盘源码、批量读写、shell、Git、PID/log、test/typecheck/build
Playwright Chrome / AX = Reality Plane    Playwright 管普通 Web；AX/Swift + screenshot 管 Chrome privileged / 系统 UI
```

### 4.1 先判问题起点，再选择 Plane

四 Plane 是职责边界，不是固定流水线。执行前先问：**当前最大不确定性最先暴露在哪一层，哪个工具能最快拿到不可替代的 authority？**

```text
Browser / UI symptom
→ Reality first
→ 普通 Web：Playwright screenshot + snapshot/DOM
→ privileged Chrome / 系统 UI：AX tree + screenshot
→ 未看清当前页面前禁止 source-first diagnosis

仓库理解 / 修改
→ Context first
→ Repomix 最小充分 scope，一次 pack 多次 grep/read
→ 再用 CodeGraph 证明结构，Local Dev 执行

纯结构关系问题，且不缺仓库上下文、不立即修改
→ CodeGraph 可直接作为第一入口

纯 Git / test / build / PID / Registry / Workspace readback
→ Local Dev 直接执行，不为机械事实额外做仓库探索

MCP runtime / relay / token / manager 问题
→ 先按 Tool-Runtime 恢复工具本身
→ 工具恢复后返回原业务 checkpoint
```

**Reality-first override 高于 Repomix-first。**`Repomix first` 的完整语义是“仓库理解/修改任务的 Context Plane first”，不是“任何问题都先 pack 仓库”。反过来，Browser 页面看清以后若已证明是源码问题，也不能继续只在 UI 猜测，必须切入 owning package。

**不要仪式化四连调用。**Repomix、CodeGraph、Local Dev、Playwright/AX 只在当前问题需要其 authority 时进入；一个工具已经返回的事实不得为了“确认”被下一个工具整域重读。

先判断任务范围，再路由：

```text
广域 / 未知 / repo-wide / 跨目录交叉审计
→ Repomix first：一次 pack 建立稳定仓库上下文
→ grep/read outputId 缩小范围
→ CodeGraph 精确证明结构关系 / blast radius
→ Local Dev 读取仍缺失的当前源码并执行修改/验证
→ 只有涉及真实 Browser/UI 时再进入 Playwright

已知 symbol / 已知实现入口，当前问题只问 caller/callee / ownership / composition / blast radius
→ CodeGraph first：直接证明结构关系并返回相关 current-on-disk source
→ 只有后续需要 package 邻接上下文或准备修改时，才补 Repomix 最小 scope
→ Local Dev 只补当前磁盘真值 / 执行验证

单包局部 bug，已经准备理解/修改实现并需要实现 + tests + config 邻接上下文
→ Repomix first：只 pack 当前 package / 最小相关目录，建立批量读取上下文
→ grep/read 同一 outputId，一次了解相关实现、测试、配置和邻接文件
→ CodeGraph 精确证明结构关系 / blast radius
→ Local Dev 只补磁盘真值并执行 batch transform / verify
→ 需要真实 Browser/UI 证据时才进入 Playwright

普通 Web / ChatGPT / Tasks 现实问题
→ Playwright 先观察真实页面并截图/snapshot
→ 需要源码归因时回 Repomix / CodeGraph
→ 需要本机日志/修改/测试时用 Local Dev

Chrome privileged / 系统 UI 现实问题
→ AX / Swift + screenshot 先观察
→ 回普通 Web 时交还 Playwright；需要源码归因再进入仓库 Plane
```

**仓库理解/修改任务默认先进入 Repomix Context Plane。** 广域与窄域的区别只在 pack 范围：窄域收敛到当前 package / 最小相关目录，广域再按证据逐级扩张；禁止为了“完整”直接 full-repo pack。CodeGraph 负责结构关系，不能替代 Repomix 的批量上下文；Local Dev 是当前磁盘与执行真值；Reality Plane 中普通 Web 以 Playwright 为真值入口，Chrome privileged / 系统 UI 以 AX + screenshot 为真值入口。纯 Git/test/command 等无需代码理解的机械动作，以及纯 Browser/UI 现实问题，可以直接进入对应 Plane。

### 4.2 各工具必须产出什么，才算被真正利用

| 工具 | 不可替代产物 | 高价值使用方式 | 典型浪费 |
|---|---|---|---|
| Repomix | 稳定 `outputId`、目录/实现/测试/配置的批量上下文 | 最小充分 pack → 同一 outputId 多次 grep → 小段 read | 每问一次重新 pack；整包灌入上下文；已知现实问题仍先 full repo |
| CodeGraph | caller/callee、composition、ownership、blast radius + 相关源码 | 一次问题导向 explore 覆盖关键链路 | 把它当 grep；它已返回源码又立刻 Local Dev reread |
| Local Dev | 当前磁盘、Git、PID/log、Registry/Workspace、真实 test/build | batch read / batch transform / batch verify；非幂等动作单独设 STOP POINT | per-file loop；把当前执行权威当仓库探索器 |
| Playwright Chrome | 普通 Web 当前 URL、DOM/snapshot、page screenshot、Console/Network | 动作前看 → one mutation → 立即看 → Owner readback | API success 代替页面成功；看不到 privileged 页面后继续猜 |
| AX / Swift helper | `chrome://` / Extension UI / 系统 UI 的可见结构与操作结果 | AX tree + screenshot 双证据；原子 privileged 操作 | 固定坐标；把 Playwright 不可 attach 误判成页面不可观察 |

信息密度的目标不是让每个工具“都出现”，而是让每一次调用都消除当前最大的未知。

工具输出或历史记录与当前磁盘冲突时，以当前磁盘/Registry/runtime 的机械事实为准。Repomix `outputId` 是 pack 时刻的稳定快照；源码发生实质变化后不要把旧 outputId 当最新磁盘真值，需要时重新 pack。

## 5. 高吞吐 Agent 执行 Harness

优化目标不是“少敲几条 shell”，而是**最小化 Agent ↔ Tool 往返次数，同时让每次调用承载更大的有效上下文**。

广域任务默认链：

```text
Repomix 从最小可解释范围开始（目录/包/相关领域）
→ grep/read 判断是否足够
→ 证据不足才向父级 / 多包 / 全仓逐层扩大
→ 只有 repo-wide 任务才 full-repo pack
→ grep_repomix_output / 小范围 read_repomix_output（不要整包灌入上下文）
→ CodeGraph 一次结构发现 / blast radius
→ CodeGraph 已返回源码直接视为 Read
→ 仅对仍缺失或需磁盘真值确认的内容做一次 read_multiple_files
→ 一次 batch transform
→ 一次 batch verify（diff/check + targeted gate + status）
→ 只有失败或发现新证据才进入下一轮
```

窄域任务默认链：

```text
Repomix pack 当前 package / 最小相关目录
→ 围绕同一 outputId grep/read，批量建立实现 + 测试 + 配置上下文
→ CodeGraph 一次结构发现 / blast radius
→ Local Dev 仅补仍缺失的磁盘真值
→ 一次 batch transform
→ 一次 batch verify
```

硬规则：

- 禁止把 `list → read A → read B → search → read C`、`edit A → edit B → edit C` 当作仓库级默认工作流。
- Repomix 必须执行“最小范围 → 父目录/多包 → 领域 → 必要时全仓”的 Progressive Context Ladder；范围升级必须有上一层证据，禁止未知任务一上来 full-repo pack/read。
- **Repomix 路径永远按其 sandbox root 解释，不按系统文件系统解释。** 当前 root 为 `/Users/agent/Desktop/proton-workspace/repos`；新 Chat 首次使用时先 `file_system_read_directory(".")` 做一次 root preflight，然后只传 `proflow/...`、`ai-agent-platform/...`、`job-search-system/...` 这类相对路径。遇到 `directory not found` 先重读 `.` 并校正相对路径，禁止直接误判 runtime/pack 故障后降级成 Local Dev per-file loop。
- Repomix pack 后优先围绕同一 `outputId` 做 grep / 局部 read；禁止无目的读取完整百万 Token 聚合输出。默认 `compress=false` 配合增量 grep/read；只有确实需要整体骨架时才考虑 Tree-sitter compression。
- 大仓库优先用目录边界和 `includePatterns / ignorePatterns / outputPatterns` 收窄业务域；先减少无关输入，不把“能 pack 全仓”误解为“每次都该 pack 全仓”。
- CodeGraph 已返回的当前源码禁止无理由重复 Read；只有 graph 与磁盘冲突、源码被后续修改、或所需区段未返回时才补读。
- 超过 2 个文件或存在多处同类 replacement 时，优先一次 `read_multiple_files` + 单次批处理；没有原生 batch edit 时，用一次 `start_process` 执行带断言、白名单和失败即停的 Python/Node transform。
- 禁止用 `write_file` chunk loop 完成仓库重构；chunk write 只适合真正的小文件创建/局部写入。
- 窄域逻辑 Batch 也必须包含一次最小范围 Repomix Context Plane，默认约 **4～6 次** Agent ↔ Tool 往返；广域任务只是扩大 pack 范围，而不是改变工具链。明显膨胀到十几/几十次时，先检查是否发生 per-file loop、重复 pack/read 或高频轮询。
- 修改后默认一次完成 `git diff --check`、changed-files、targeted test/typecheck/build（按 blast radius）和 `git diff/status`，不要逐文件回读确认。

自然长步骤仍保持边界：release/install/setup/真实 Browser Journey、外部 mutation 等不能为了“少调用”串成不可恢复的巨型命令。长步骤固定 `ROUND_ID + 自己的 PID + 独立日志 + STOP POINT`；本机执行面可能被多个 Chat 共用，只管理本轮登记的进程，避免高频轮询。

详细执行法见 `03-自动化知识库/基础动作/Chat-高吞吐本地工程执行.md`；工具 runtime / 连接恢复见 `03-自动化知识库/基础动作/Tool-Runtime-gptweb-mcp.md`。

## 6. 非幂等操作

publish、create remote resource、migration、install/update 等发生 timeout/UNKNOWN 时：**先恢复权威状态，再决定是否继续；禁止盲重试。**

npm publish 前后都做 Registry exact readback；同版本已存在绝不重复发布。Registry readback 网络 UNKNOWN 不等于 MISSING。

## 7. 最小整改与验证

真实失败 → owning package → 最小改动 → targeted regression + package typecheck（按影响补 build）→ 发布 → Registry exact → `platform update --package` → 回原用户场景。

已经证明稳定且与本次失败无关的昂贵步骤不重复。`platform update` 稳定后，日常 repair loop 默认禁止 Fresh + 全量 install。

**进入真实自动化测试 / 人工模拟验收阶段后，默认进入“最小影响修复模式”。** 此时目标是修复当前可复现 blocker，而不是顺手做架构升级、抽象重构或机制补全。每次改码前必须先自问并留下机械答案：

```text
1. 这是当前真实失败的 owning root cause，还是只是一种更漂亮的设计？
2. 现有 Promise / Owner truth / idempotency / recovery 机制真的做不到，还是只是当前 composition 写错了？
3. 是否必须新增 Scheduler / Queue / Message / Framework / Public Contract？若非必要，禁止引入。
4. 这次改动会不会触碰已 PASS / Frozen / 与当前失败无关的模块？
5. 能否把修复缩小成一个 package、一个行为、一个 regression test？
6. 修完能否直接回到同一失败 checkpoint 重放，而不是重跑整条 Journey？
```

执行节奏固定为：**一个假设 → 一个最小改动 → 一个 targeted regression → 同一现场 readback**。没有新证据不得把多个候选问题合并成一次大修；若最小修复仍不足，再进入下一轮。仅当现有冻结语义无法表达正确行为，并已有证据证明是 SPEC_GAP / CONTRACT_CONFLICT 时，才允许升级为架构或 Contract 议题。

Timeout 也遵守同一纪律：先证明 timeout 的 owner、阶段语义与真实延迟，再调整；禁止用“把 12s/45s 改大”掩盖调度、恢复或 composition 根因。

## 8. 发布物与 tarball

真实验收只认 npm Registry 发布物。local tarball / `.tgz` / link / workspace source override 不能替代真实 npm 安装/更新。

`pack/tarball` 只允许作为 publishability 异常、files 配置或打包内容怀疑时的诊断手段，不进入常规 Fast Loop。

## 9. 安全与环境

- **用户前台焦点属于用户。** 普通 Web / ChatGPT / ProFlow Tasks 页面必须优先用 Playwright 后台操作与 page screenshot，不得为了观察或截图默认 `activate Chrome`、移动真实鼠标键盘、截整个桌面。只有 `chrome://extensions`、扩展工具栏、Load unpacked、系统 picker/确认框等 privileged UI 才允许短暂激活 Chrome；离开临界区后立即回到后台自动化。
- **Chrome privileged UI 固定采用“一次前台原子回合”。** Playwright 不能直接控制 `chrome://` / `chrome-extension://` 时，禁止为了追求“更程序化”连续试 privileged navigation、extension-origin navigation、AppleScript JS、AX 菜单等多条路径并反复抢用户前台。正确顺序固定为：`一次 activate Chrome → 一张 fresh privileged screenshot 定位页面/目标 → 一次必要 mutation → 立即一张 screenshot 验证 → 回后台用 platform/Owner/heartbeat authority readback`。动作返回值不能替代截图；若一张截图已经足够定位目标，就不得继续探索第二种 UI 自动化方案。Extension Manager 中卡片位置不是 identity：禁止按“第几个卡片”或全局 AX 顺序定位 Reload/Remove。**Extension ID + 名称只允许作为身份锚点，不得假设 AX ancestor / 最小父容器就是可靠 card boundary。** mutation action 必须再经过当前 Chrome fresh reality 下独立可验证的位置/几何关系确认；Remove 等 destructive action 还必须在原生确认 UI 中再次核对目标名称/身份，任一层不一致立即 STOP。未经当前 Chrome 版本和当前页面结构 fresh validation 的 locator/启发式，不得沉淀为长期稳定规则。
- 本机共享 MCP runtime 只能由唯一正式 manager `com.sayhello.gptweb-mcp` 管理；任何 Chat/排障脚本禁止创建私有 LaunchAgent、KeepAlive/StartInterval job 或第二套 supervisor。需要 restart 只走统一 `gptweb-mcp restart`；异常先查 manager 数量，再查 MCP 本体。
- 不打印、不提交 token、Bearer、API Key、credential。
- 未经授权不删除远端 Tunnel/GPT 等不可逆或共享 external resource。
- 用户明确说明的外部环境条件（例如模型设备暂时被占用）不得擅自升级为产品 bug。

## 10. 公共上下文维护

公共上下文不是只读接管材料。机械 authority、checkpoint、blocker、root cause、tool route 或稳定执行知识发生变化时，按 `01-长期规则/02-公共上下文治理规则.md` 的 Event Trigger **立即写回唯一 owner**；若 `CURRENT` 已落后于现实，先修复 `CONTEXT_DRIFT` 再进入下一重大动作。每轮结束再做 Round Closeout 作为第二道漏项检查。不要把包 SOP、Round 日志重新堆回本文。
