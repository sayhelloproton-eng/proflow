# ProFlow｜执行纪律与项目 Overlay

> 本文件只保留 ProFlow 项目特有的 Frozen Contract、产品真值、发布物、用户路径和安全边界；不维护跨项目执行 SOP。

## 1. 共享协议

```text
Local Engineering
→ /Users/agent/Desktop/proton-workspace/skills/chat-local-engineering-protocol/SKILL.md

Local Acceptance Automation
→ /Users/agent/Desktop/proton-workspace/skills/chat-local-acceptance-automation-protocol/SKILL.md
```

Engineering Decision、源码读取/修改/验证、工具选择与吞吐由 Engineering Skill 唯一拥有。Browser/UI、CLI/PTTY、MCP/runtime/auth、timeout/UNKNOWN/recovery、Acceptance mode、checkpoint automation、telemetry 由 Acceptance Skill 唯一拥有。

项目旧文档中的同类通用方法不再拥有 authority。

## 2. ProFlow 授权与 Frozen 边界

- 用户是重大结构、Frozen Contract、Owner/State、范围扩张的裁决者。
- “整理 / 顺手优化 / 看起来更合理”不是产品修改授权。
- 已 PASS/FROZEN 能力只有新的真实 regression evidence 才允许按正式设计局部重开。
- Real 阶段只处理当前 owning blocker，不借机改写稳定产品语义。

## 3. ProFlow 产品真值

```text
Formal Spec / Frozen Contract = 产品应该是什么
Git/source                    = 当前实现
Registry                      = 发布事实
Product Workspace             = 安装/物化事实
Owner / external runtime      = 当前真实产品运行事实
CURRENT                       = 当前项目 checkpoint / blocker / next action
```

历史文档不能覆盖更晚的机械 authority；共享 Skill 决定如何取得/恢复这些事实，但不改变它们的业务含义。

## 4. 用户路径与真实产物

- ProFlow 真实 Acceptance 必须通过正式公开产品入口成立；不得直接写 `.proflow`、Owner DB、pairing evidence、node_modules 或远端资源状态来制造 PASS。
- npm Registry 发布物、真实 Product Workspace adoption、真实 Browser/Owner/runtime 是不同产品证据层，前一层不能冒充后一层。
- local tarball/link/workspace override 可以用于工程诊断，但不能替代要求 real npm/real Workspace 的正式产品验收。

具体如何 reconcile UNKNOWN、如何回 SAME SCENE、如何操作 Browser/CLI，统一按 Acceptance Skill，不在此复制。

## 5. ProFlow 特有安全边界

- 未经授权不删除远端 Tunnel、GPT 等共享/不可逆资源。
- 不打印、不提交 token、Bearer、API Key、credential。
- 用户明确的外部环境条件不得擅自升级为产品 bug。
- 当前正式 Spec/Frozen Contract 不能被旧实现、旧 Runbook 或测试便利性静默改写。

## 6. 项目 Context 写回

机械 evidence 证明 ProFlow 的 authority/checkpoint/blocker/产品 root cause/next action 变化时，按 `01-长期规则/02-公共上下文治理规则.md` 更新项目 owner。

通用 Engineering/Acceptance 方法变化不写回 ProFlow Context；应进入对应共享 Skill 的 evidence/evolution 路径。CURRENT 只保留项目事实，不再复制通用执行协议。
