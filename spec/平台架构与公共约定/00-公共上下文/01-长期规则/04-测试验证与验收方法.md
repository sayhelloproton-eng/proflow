# 测试验证与最终验收方法

> 本文件只定义 **ProFlow 产品必须证明什么**。ChatGPT Chat 如何操作 Browser/CLI/PTTY/MCP、如何分类失败、如何从 checkpoint 恢复、如何处理 timeout/UNKNOWN、如何选择 SAME_SCENE/FAST_REPLAY/FULL_FRESH，唯一服从 `/Users/agent/Desktop/proton-workspace/skills/chat-local-acceptance-automation-protocol/SKILL.md`。

## 1. 当前方法定位

Phase 3 早期使用全量交叉审计，适合架构与实现尚未收口阶段。`READY_FOR_SMOKE = YES` 之后，当前主任务已经变为 **最终真实验收**。

这里定义 Real-1～Real-6 与 Deployment Closeout 的 ProFlow 产品验收目标，不替代 `06-测试计划` 中已冻结的 Unit → Domain → Contract → Integration → Real E2E → Fault/Recovery → Evidence 正式测试层级。

结构性证明只能作为前置证据；最终阶段必须证明 Mock/静态门无法证明的真实外部行为、真实 Owner state、真实 effect/result/evidence。

## 2. Real 阶段产品目标

- **Real-1**：按正式 Test Plan 证明基础产品主链的真实外部依赖与运行事实，不能用 Mock 冒充真实 readiness。
- **Real-2**：三个 Agent Package → 真实 Custom GPT → Role register → durable identity → reload/reopen 后仍成立 → 至少一个真实 Gateway/Carrier identity probe。
- **Real-3**：按冻结 J0～J4 产品 Journey 证明 Task / Node / Worker / Browser Carrier / Owner Facts 一致；只有真实 Journey 证据成立才可 PASS。
- **Real-4**：真实 askPeer/replyPeer + Approval + Effect；必须有 Owner durable state / real effect evidence，不能用 API 200 替代。
- **Real-5**：证明 File、Browser、FAST、REASON、调度与联合执行；真实 Chrome/Custom GPT/手机模型不能由 Mock 替代。
- **Real-6**：按正式 Fault/Recovery Test Plan 证明中断、重启、lost response、duplicate/UNKNOWN 等产品恢复语义；阶段最终是否需要完整 J0～J6 由正式测试计划决定。

具体“如何自动化执行和恢复”不在本文件展开，统一由 Acceptance Skill；项目 Flow 只提供当前业务顺序、identity 与 checkpoint。

## 3. Deployment 系统端到端验收的产品主视角

**Deployment Closeout 的主测试身份固定为：模拟第一次使用 ProFlow 的普通用户，从真实产品入口进行系统端到端测试。** 这不是开发者内部自测，也不是把 package tests / CLI exit code 跑绿。

产品要求：

```text
普通用户只使用公开产品入口和真实 UI / CLI
→ 不依赖源码或内部 package CLI 才能完成正常部署
→ 不手改 .proflow / DB / shared facts / evidence 制造成功
→ 不要求用户理解 moduleRef、内部端口、Tunnel ownership 等实现细节
→ 最终用户看到的 READY 必须与真实外部/Owner/runtime 状态一致
```

调试期间可以由总控使用内部证据定位实现缺陷，但这不能替代公开用户路径最终重新成立。如何保存现场、定位 first divergence、修复后回原 scene，由共享 Engineering / Acceptance Skill 负责。

## 4. Deployment Product Acceptance 四个产品门

1. **Cognitive Load / 用户心智门**：普通用户只理解产品级步骤和当前唯一动作；若必须理解内部 module/shared facts/端口/ownership 才能完成正常部署，则 FAIL。
2. **Automation / 产品自动化门**：机器可确定且产品应该自行掌握的事实，不应反复要求用户手工输入或执行内部命令。
3. **CLI Interaction / 产品交互门**：公开 CLI 必须明确当前阶段、原因、所需动作、成功/失败和下一步，并具备正式设计要求的取消/重入/幂等/恢复语义。
4. **Default Output / 默认输出门**：正常输出聚焦 `当前状态 + 唯一 root cause + 下一步 + 最终结果`；内部 traversal/owner 诊断默认不暴露给普通用户。

判定关系：

```text
技术主链真实跑通
= DEPLOYMENT_TECHNICAL_MAINLINE = PASS

技术主链 PASS
+ 用户心智门 PASS
+ 产品自动化门 PASS
+ CLI 交互门 PASS
+ 默认输出门 PASS
= DEPLOYMENT_SUCCESS = YES
```

这些是 ProFlow 产品要求，不是 ChatGPT 自动化工具 SOP。

## 5. PASS / Evidence 原则

`Business Fact`、`Evidence`、`Log` 必须分开。真实 PASS 至少要能回答：验收目标是什么、真实环境是什么、实际产品行为是什么、Owner/external reality 是什么、是否存在 fake/mock/bypass、为什么证据满足 Frozen Contract。

以下均不能单独证明 REAL PASS：

- unit / contract / conformance 全绿；
- HTTP 200 或进程存活；
- CLI exit 0；
- README / schema 看起来正确；
- fake URL / fake provider / mock carrier；
- 手工修改 DB/内部 JSON 绕过正式路径。

产品修复完成后必须重新证明原失败产品行为符合 Frozen Contract；具体 replay 强度与自动化恢复方式由 Acceptance Skill 决定。

## 6. 设计冲突

若真实 evidence 表明正确实现必须改变 Frozen Owner/State/Contract，或外部系统现实与冻结假设冲突，必须进入正式 `SPEC_GAP / CONTRACT_CONFLICT / EXTERNAL_BEHAVIOR_MISMATCH` 裁决；不能为了让自动化通过而静默改写产品设计。
