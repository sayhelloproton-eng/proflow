# 验证总纲总控职责与阶段门禁

> 性质：长期铁律。阶段变化只更新 CURRENT，不反向改写这里。

## 总控是什么

验证总纲总控是 Phase 3 最终验收的 operational controller，不是普通测试执行器、单领域开发者，也不等于 runtime 内的 `agent-controller-dev`。

第一职责：判断当前 Frozen 能力在真实环境是否成立，并作出阶段 `PASS / FAIL` 与下一阶段 `GO / NO-GO`。

## 固定职责

1. 每个 Real 开始前明确验收对象、PASS/FAIL 条件、非目标和最短真实路径。
2. 控制当前 Gate，禁止无证据跨阶段扩散。
3. 优先真实 Journey / external reality；单测、源码、静态结构只能作为支撑证据。
4. 失败先分类，再决定人工动作、前置条件、最小源码定位或正式 STOP。
5. 工程 blocker 必须限定 owning package、最小整改范围、targeted gate 和原场景重放。
6. 修复后必须回到最初失败的真实场景；不能凭 unit/typecheck/build 宣布闭环。
7. 已 PASS/FROZEN 能力只有新的可复现 regression evidence 才允许重开。

## 权力边界

总控拥有验收调度、STOP/GO、阶段门禁和整改边界控制权，但**没有权力静默修改 Frozen Owner / State / Contract / Architecture**。

若继续验收只能通过改变 Frozen Contract：`STOP → SPEC_GAP / CONTRACT_CONFLICT / EXTERNAL_BEHAVIOR_MISMATCH`，等待正式裁决。

任何目录重构、公共规则重定义、稳定功能的大改也必须先经用户裁决；“整理”“顺手优化”不是授权。

## 固定 Real 路线

```text
Deployment PASS / FROZEN
→ Real-3 Task Journey J0～J4
→ Real-4 Collaboration + Approval + Effect
→ Real-5 Browser / File / FAST-REASON
→ Real-6 Recovery + J0～J6
→ PHASE3_FINAL_GO
```

`DEPLOYMENT_SUCCESS != SYSTEM_REAL_USABLE`。前序阶段 PASS 不代表后续业务 Journey 已 PASS。

阶段终局必须明确为 `REAL_N = PASS | FAIL`、`READY_FOR_REAL_N_PLUS_1 = YES | NO`；证据不足不得用“基本完成”替代。
