# 公共上下文治理规则

> 目标：降低跨 Chat 接管成本，同时保证 ProFlow 项目事实与 ChatGPT Chat 跨项目执行协议各自只有一个 owner。

## 1. 所有权

```text
ProFlow Formal Spec / Test Plan
→ 产品架构、Owner、Contract、正式验收要求

02-当前接力/CURRENT.md
→ 当前项目 stage / checkpoint / blocker / next action

01-长期规则
→ ProFlow 低频稳定的项目治理、安全与 Frozen 边界

03-自动化知识库（兼容名称）
→ ProFlow 项目特有 package/resource/Journey/Flow 事实、顺序与证据

chat-local-engineering-protocol/SKILL.md
→ ChatGPT Chat 本机工程 mechanics 唯一真源

chat-local-acceptance-automation-protocol/SKILL.md
→ ChatGPT Chat 本机 Acceptance 自动化 mechanics 唯一真源

90-历史记录
→ 旧 handoff、Round、事故、已结束阶段与原始 evidence
```

共享 Skill 的绝对路径：

- `/Users/agent/Desktop/proton-workspace/skills/chat-local-engineering-protocol/SKILL.md`
- `/Users/agent/Desktop/proton-workspace/skills/chat-local-acceptance-automation-protocol/SKILL.md`

## 2. 禁止第二自动化真源

项目 Context 不再拥有跨项目 Browser / CLI / PTY / MCP / runtime / auth / timeout / UNKNOWN / recovery / Acceptance mode / testing harness / logging / tool-routing / high-throughput engineering 方法。

旧项目文档中这类完整 SOP 应删除或降级为兼容指针；项目 package/flow 文档可以保留与 ProFlow 产品直接相关的：公开入口、资源 identity、Frozen Contract、产品状态、业务顺序、项目级安全限制、PASS/FAIL/STOP 条件和历史机械证据。

同一通用规则不得以“高风险短句镜像”为理由在 README/CURRENT/长期规则/Runbook 多份维护。需要提醒时只写共享 Skill 指针或产品特有约束，不复制第二套条件/例外。

## 3. 项目知识归属

```text
所有 ProFlow Chat 都必须知道的项目事实/边界？ → 01-长期规则
下一 Chat 接着做必须知道的当前状态？          → CURRENT
某 ProFlow Package / 外部资源的产品事实？      → 03-自动化知识库/包能力
Deployment / Update / Real-N 的产品顺序？      → 03-自动化知识库/流程
跨项目本机工程方法？                           → Engineering Skill
跨项目 Acceptance 自动化方法？                 → Acceptance Skill
单轮日志、PID、截图、事故原始 evidence？       → 90-历史记录
产品 Owner / Contract / State / Test Plan？     → 正式 spec / Test Plan
```

“以后还能复用”不足以把通用自动化知识写回 ProFlow；先判断它是 ProFlow 产品知识，还是共享 Skill 应吸收的跨项目 mechanics。

## 4. 当前事实写回

公共上下文仍是项目状态控制面。以下 **项目事实** 被机械证明变化时，应同步对应 owner：

```text
PROJECT_AUTHORITY_CHANGED   Git / Registry / Workspace / Owner / runtime 的项目事实改变
CHECKPOINT_CHANGED          当前 Journey / Gate / STOP POINT 前进或回退
BLOCKER_CHANGED             旧 blocker CLOSED 或新 blocker 被确认
ROOT_CAUSE_CONFIRMED        当前产品 owning boundary 被机械证明
PROJECT_FLOW_CHANGED        ProFlow 特有业务/Journey 顺序改变
REUSABLE_PROJECT_KNOWLEDGE  稳定的 ProFlow package/resource 产品知识成立
```

通用工具路由、Browser 操作方式、timeout/recovery 方法发生变化时，不写回项目 owner；按共享 Skill 的 evolution contract 处理。

## 5. 写回矩阵

| 新事实/经验 | 唯一写回位置 |
|---|---|
| 当前进度、版本、blocker、checkpoint、下一项目动作、STOP POINT | `02-当前接力/CURRENT.md` |
| ProFlow Package / 外部资源稳定产品事实 | `03-自动化知识库/包能力/<owner>.md` |
| Deployment / Update / Real-N 项目编排 | `03-自动化知识库/流程/` |
| 跨项目本机工程 mechanics | Engineering Skill evidence/evolution |
| 跨项目 Acceptance automation mechanics | Acceptance Skill evidence/evolution |
| 单轮事故、截图、耗时、旧 acceptance 原始 evidence | `90-历史记录/` |
| 产品 Owner / Contract / State / Test Plan | 正式 `spec/` / Test Plan |

## 6. CURRENT 与 REQUIRED_CONTEXT

CURRENT 只保留当前 ProFlow 项目事实、checkpoint、blocker、next action、项目级 mutation authority 和 DO_NOT_REPEAT。不得复制共享 Skill 的 Engineering Decision、tool sequence、Browser/CLI/MCP SOP、polling、timeout、UNKNOWN、recovery 或 test harness 规则。

`REQUIRED_CONTEXT` 只列 Core 读取后额外需要的 **ProFlow Spec / project Runbook**。旧通用 Primitive 兼容指针不应作为新的必读协议；涉及对应 mechanics 时直接按共享 Skill 条件加载 references。

## 7. Round Closeout

每个有意义 Round 只检查：

1. CURRENT 的项目事实/checkpoint/blocker 是否变化；
2. ProFlow package/resource 是否产生新的稳定产品知识；
3. ProFlow Journey/Flow 是否变化；
4. Formal Spec/Test Plan 是否因真实证据需要 Amendment；
5. 是否出现应交给共享 Engineering/Acceptance Skill 的跨项目 evidence；
6. 是否存在只应进入历史的原始 evidence。

共享 Skill 候选只作为 evidence 交给其 evolution 机制，不在项目 Context 复制规则。

## 8. 失忆接管 Gate

只给新 Chat：当前共享 Skills + `README / 长期规则 / CURRENT / REQUIRED_CONTEXT`，它应能回答 ProFlow 是什么、当前 checkpoint、下一项目动作、产品真源、项目级禁止重做项、PASS/FAIL 条件，以及当前动作需要哪一个共享 Skill。

如果必须读取旧 Browser/CLI/MCP/高吞吐项目 SOP 才知道“怎么自动化”，说明迁移未完成；如果缺的是 ProFlow 产品 identity/Contract/checkpoint，则补项目事实，而不是把共享协议复制回来。

## 9. 历史与兼容文件

正常换 Chat 的当前交接只依赖 CURRENT 与固定接管模板。旧 handoff/事故只进入 `90-历史记录`。

旧通用自动化文件可为避免链接失效保留为短兼容 stub，但其正文不得再维护规则。历史形成过程由 Git history / `90-历史记录` 保存，不参与当前裁决。
