# 13 · 测试验收：M1 ~ M4

## 1. [FROZEN] M1 — Contract Gate

纯自动化测试，必须覆盖：

- `model-contracts` 类型编译；
- Reasoning Spec 定义合法；
- input/output runtime schema；
- unknown→typed boundary；
- FAST/REASON/AUTO mode rules；
- Capability Proposal 只能选候选能力；
- one proposal per inference；
- bounded repair；
- error normalization；
- RuntimeStatus schema。

**停止门**：M1 不通过，禁止接真实模型。

## 2. [FROZEN] M2 — Model Capability Gate

对部署配置的真实 API 模型执行。

FAST：

- text；
- no-thinking 行为；
- structured output；
- Vision（若声明）；
- context/output limit sanity；
- latency baseline。

REASON：

- text；
- thinking/reasoning；
- structured output；
- Vision（若声明）；
- latency baseline。

**停止门**：声明能力与实测不一致，role 标记 UNAVAILABLE。

## 3. [FROZEN] M3 — Reasoning Spec Scenario Regression

每个进入生产控制路径的 Spec 都必须有固定 Case，而不是只测普通聊天。

第一批建议场景族：

```text
execution.command-risk
execution.evidence-conflict
execution.unknown-recovery
browser.page-state
browser.progress-gap
system.health-assessment
capability.proposal
```

每组至少有：

- 正例；
- 否例；
- 边界；
- 低置信/ESCALATE；
- invalid output defense。

指标优先：

- route correctness；
- schema validity；
- decision correctness；
- false-allow / false-deny 的关键风险。

## 4. [FROZEN] M4 — Stability / Performance Gate

必须按真实单 Lane 连续跑，而不是单个 benchmark：

```text
FAST
FAST
FAST + image
FAST
REASON
FAST
...
```

记录：

- sustained success rate；
- schema pass rate；
- routing pass rate；
- queue latency；
- inference latency；
- total latency；
- timeout/error distribution；
- FAST/REASON role switching 稳定性。

## 5. [FROZEN] 替换模型的验收规则

任何 FAST/REASON 模型替换都必须重新跑：

```text
M2 + 受影响 Reasoning Specs 的 M3 + 关键 M4
```

不能只因为 API schema 相同就认为等价。

## 6. [DEFERRED] Deployment verify/doctor

M2/M4 的具体 CLI 编排留给最终 Deployment Domain；本领域只冻结测试语义与 PASS 标准。

## 当前正式约束：测试门

M1 增加 runtime validation/contract provider tests；M2/M3 继续以真实 Capability Profile + ReasoningSpec 场景验收；M4 保持真实需求相关 latency/queue/stability/sustained gate，不追求无业务依据 QPS。跨域关键 Contract 变化必须跑受影响 E2E。

## 7. 2026-08-14 Observer / Assessment 推理验收追加门

本节是 J0～J6 / X1～X7 架构裁决后的增量门禁，不新增 Model Domain 业务事实。

### 7.1 Task Diagnostic

Task Observer 的正常 READY / result-ready / peer-reply / reopen progression **不得调用模型**。只有 deterministic facts 无法安全解释的单 Task 异常，才允许调用 REASON，例如：

```text
facts conflict
Execution UNKNOWN
repeated Carrier recovery failure
long stalled with no single blocker
multiple abnormal signals requiring diagnosis priority
```

必须验证：

- REASON 输出仅为 `finding / probableCause / confidence / recommendedNextObservation / recommendedRecoveryAction / needsHumanAttention` 等派生判断；
- 不得通过模型输出直接 `completeNode/reopenNode/approve/retry dangerous effect`；
- Task/Execution/Collaboration current facts 仍是最终权威；
- REASON 不可用时只延后诊断，不得阻塞正常 Task 主链。

### 7.2 System Assessment

System Observer 是低优先级**全系统评估器**。测试必须覆盖至少八类 bounded view：

```text
Task
Agent / Worker
Collaboration
Execution
Carrier
Model
Deployment / Services
Logs / Artifacts / Evidence summaries
```

输入不应默认包含完整源码、完整 Task 文档、全量日志、完整 patch 或 raw secret。

### 7.3 分批、carry-forward 与 Global Synthesis

不能把理论 context window 当作有效系统评估负载。必须真实验证：

1. Layer 1 deterministic compact snapshot；
2. Layer 2 concern/domain batches；
3. 显式 previous unresolved findings / carry-forward；
4. targeted drill-down；
5. Layer 3 global synthesis 能识别跨域关联，而不是简单拼接分批摘要。

默认 concern batches 可按：

```text
A Task + Worker
B Execution + Approval
C Collaboration + Carrier
D Model + Deployment + Health
```

但 batch 划分是 caller/application 策略，不新增 Model Runtime scheduler/store。

### 7.4 手机 REASON 真实有效负载门

M4 必须增加 System Assessment 的真实负载测试：记录每批输入大小、推理耗时、结构化输出成功率、跨批引用保持率、global synthesis correctness、drill-down correctness，以及 foreground business request 对 background assessment 的抢占效果。

**停止门**：如果一次性输入在 token 上可接受但实际推理质量显著下降，必须缩小 bounded view / batch；禁止以“模型理论支持大上下文”为由强行单次全量输入。
