# 版本、升级、兼容性与模板迁移

## 1. 版本维度

v1 仅保留必要维度：

1. `moduleVersion`：内部 package 或 external adapter 版本；
2. `moduleContractVersion`；
3. `templateVersion`；
4. `platformCompatibility`；
5. Provides/Requires contract version；
6. External `resourceVersion?`（动态事实）。

不建设第二套独立“Deployment Version”体系。

## 2. Upgrade 是 v1 P0 能力

原因：五个 Deployment 基础包就是为了让后续各领域 npm 包、服务和外部资源长期可统一管理、测试、升级。

## 3. Upgrade Plan

Upgrade 只以当前 Workspace `package.json` 中已安装的 Managed Module Set 为对象，不因为 Registry 出现新的 optional package 就扩大安装集合。目标版本直接来自当前 npm Registry metadata，不要求另一个源码/target Workspace。

```text
Installed / Current Reality
→ Registry target version for the same installed package
→ Target Module Set/Versions
→ Contract Compatibility
→ Provides/Requires Compatibility
→ Template Migration requirement
→ Conformance evidence
→ Config Migration
→ External Resource Actions
→ Data Migration primitive（若领域提供）
→ stop/start ordering
→ verify
```

## 4. Data Migration

数据库/schema migration 归数据 Owner 领域实现。Deployment 只：

- 识别 migration requirement；
- 计划调用公开 migration primitive；
- 安排顺序；
- 记录结果；
- verify。

## 5. Template Migration

Template 升级不等于 Module package upgrade。

若旧 Template 仍满足 Contract/Compatibility/Conformance，可以继续使用。

强制迁移条件必须明确，不因“有新模板”就大规模重写。

## 6. Verification History

按版本保留：

```text
module 1.0.0 PASS
module 1.0.1 FAIL
module 1.0.2 PASS
```

External Resource 没有传统版本时，以 adapterVersion + resource identity/config fingerprint 建立 Verification Record。

## 7. Rollback

v1 不做自动事务式 rollback。

Package upgrade 由目标 Workspace 的真实 package manager 更新 package manifest/lockfile/node_modules；升级前后的 Descriptor 都以各自真实 package version 为准。Package lifecycle scripts 不替代 Deployment migration/lifecycle contract。

Upgrade verify fail：

```text
STOP
→ 记录 FAIL
→ doctor
→ 生成 repair 或 target-old-version Plan
```

这样足够稳定且避免复杂补偿引擎。

## 8. Registry 目标版本的升级前兼容性门

Registry-backed upgrade 不允许先修改 Workspace package 再读取目标 Descriptor。正式流程必须是：

```text
当前 Workspace Descriptor
→ npm Registry exact package/version
→ npm pack --ignore-scripts 到系统临时目录
→ 读取 package/proflow.module.json
→ 校验 packageName/moduleVersion/moduleRef
→ 对完整目标 Managed Module Set 构建 dependency graph
→ compatibility assessment
→ 生成 Upgrade Plan
→ Apply package mutation
```

`proflow.module.json` 是 package-owned、随版本发布的静态 Module Descriptor；`package.json.proflow.manifest` 只负责指向它，不复制第二套兼容性合同。临时 tarball/manifest 只用于规划期读取，读取结束必须清理。

若目标版本存在 breaking changes：

- 声明 `migrate` lifecycle：Plan 必须显式包含 migration step，随后重新 verify；
- 未声明 `migrate`：在任何 package mutation 前以 `UPGRADE_FAILED` 停止；
- 不允许“先升级再发现不兼容”。

## 9. Package Release 与 Deployment Upgrade 的边界

正式 npm package 的版本规划、Workspace 内部依赖传播和 Registry publish 统一使用仓库根 pnpm release management；Deployment Domain 不再维护第二套 package release planner。package release 的 canonical 规则见 `spec/平台架构与公共约定/02-契约/03-版本与兼容性约定.md`。

Deployment 只消费已经形成的 package/module 版本事实，并要求：

```text
package.json.version
= proflow.module.json.moduleVersion
= runtime Deployment Descriptor.moduleVersion
```

该等式由 `pnpm release:sync` / `pnpm release:sync:check` 机械维护。Package Version 的 bump 不自动改变 Contract Version；若 Public Contract 本身发生兼容性或 Breaking Change，仍必须按公共版本与兼容性约定独立升级对应 Contract Version。

当前五域第一版尚未全部完成真实验收时，package release 限制在 `0.1.x` patch-only；这不改变 Upgrade 对 Registry target Descriptor、dependency graph、migration 与 verify 的既有要求。
