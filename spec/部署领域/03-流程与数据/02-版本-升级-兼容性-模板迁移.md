# 版本同步、兼容性与模板迁移

## 1. 没有独立 Upgrade CLI

`platform upgrade` 已删除。版本同步是 `platform install` 的幂等职责：

```text
missing → install
old     → update
same    → no-op
```

目标是私有 scope 下当前完整 ProFlow package set，而不是旧 installed-only upgrade plan。

## 2. Package Manager Ownership

npm/pnpm/yarn 负责真实 package dependency resolution、manifest/lockfile/node_modules mutation。Platform 不根据 `provides/requires` 或 `installRequires` 计算 npm closure。

## 3. 安装后的真实性

Package mutation 完成后，Platform 必须重新读取 Workspace 的实际 package/version 与 Module descriptor；不能仅凭计划值宣布成功。

保持：

```text
package.json.version
= proflow.module.json.moduleVersion
= runtime descriptor.moduleVersion
```

该一致性继续由仓库 release/sync/conformance 机械门维护。

## 4. Contract compatibility

Module Contract 与 Runtime `provides/requires` 的版本兼容仍是正式事实，但不再形成 Upgrade Plan/Apply workflow。运行拓扑问题由 architecture/conformance gate 与 start 前 Module-owned validation 暴露。

## 5. Data / Template migration

数据 schema migration 逻辑永远归数据 Owner Domain；Template 更新也不自动强迫所有 Module 重写。只有 owning package 明确需要时，由 package 自己提供迁移能力和文档，Platform 不建立统一 migration planner。

## 6. Failure semantics

Install 同步失败：命令失败并保留可观察的 package-manager 现实；不自动 rollback，不生成 repair plan，不制造 `BROKEN/UPGRADING` 状态机。

## 7. Release 边界

正式 npm package 版本规划、内部依赖传播和 Registry publish 继续使用仓库根 release management。Platform CLI 只消费 Registry 与 Workspace 已存在的版本事实，不维护第二套 release planner。
