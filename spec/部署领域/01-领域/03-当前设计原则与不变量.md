# 部署领域｜当前设计原则与不变量

## 1. Platform CLI Surface

Platform 一级 CLI 只保留：`modules`、`docs`、`install`、`uninstall`、`start`、`stop`。

已删除的 `search/plan/apply/upgrade/preflight/restart/status/verify/doctor/manifest` 不得作为当前用户流程重新出现。内部 primitive 可以存在，但不能重新成为用户心智。

## 2. 所有权

```text
Module / package owns logic and truth.
Platform CLI owns discovery, dispatch, aggregation and ordering.
Package manager owns npm dependency operations.
```

Platform 不建立第二套 Module validation/runtime/repair/retry/rollback truth。

## 3. Package / Module / Runtime 边界

`Package != Module != Service != Process`。所有正式 ProFlow package 进入 Module Governance；library 不伪造 service lifecycle，运行型 Module 自己拥有 validate/start/stop/status truth。

## 4. Install / Uninstall

`platform install` 面向整个 Workspace：动态发现私有 scope 下完整 ProFlow package set，并尽量一次 package-manager transaction 同步。不存在 Core、`installRequires` 或 install closure。

`platform uninstall` 只删除当前 Workspace 的 ProFlow package dependencies；永远不自动删除 `.proflow`。

## 5. Runtime Dependency

`provides/requires` 只描述 Runtime Module topology，用于 docs 与 start/stop ordering；npm/pnpm/yarn 自己负责 package dependency graph。

## 6. Modules / Docs

`platform modules` 只聚合 Module 自己产出的 `configStatus/missingConfig?/runtimeStatus`。

`platform docs` 只聚合 Module 自己声明的 `provides/requires/configSlots/documentation`。

## 7. Start / Stop

`platform start`：发现 Module → 构图 → 先分发全部适用 Module validate/preflight（fail-fast）→ 全部通过后按依赖顺序 start（fail-fast）。Platform 不实现 Module 私有检查，也不自动 rollback。

`platform stop`：按逆依赖顺序分发 Module stop，fail-fast；不隐式做 verify/repair。

## 8. Workspace 数据

`.proflow` 属于 Workspace / 用户数据与本地 metadata，可跨 uninstall/reinstall 保留。Binding 只是 Workspace-local metadata，不再是 global lifecycle state machine。

## 9. 外部资源与 Carrier

Browser、ChatGPT Carrier、Dev Tunnel、Model Provider 等仍由各自 owning Module 表达配置、状态、验证和人工条件。Platform 只分发/聚合，不把这些领域逻辑搬进 CLI。

## 10. 收官边界

本轮只完成六命令产品减法及其必要 Contract/Template/Conformance/测试迁移。任何不阻塞冻结 Gate 的领域问题记录为 `OUT_OF_SCOPE_DOMAIN`，不得扩散整改。
