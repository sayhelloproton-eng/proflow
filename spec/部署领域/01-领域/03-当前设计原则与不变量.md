# 部署领域｜当前设计原则与不变量

## 1. Platform CLI Surface

Platform 一级 CLI 固定为七个：`install`、`uninstall`、`status`、`setup`、`docs`、`start`、`stop`。

`modules/search/plan/apply/upgrade/preflight/restart/verify/doctor/manifest` 不得作为 Platform 用户命令、别名或隐藏 route 复活。Module 自身可以继续提供真实业务 extra command，Platform 不代理、不解释。

## 2. 所有权

```text
Module / package owns logic and truth.
Platform CLI owns discovery, ordering, forwarding and aggregation.
Package manager owns npm dependency operations.
```

Platform 不建立第二套 Module config/status/validation/runtime/repair/retry/rollback truth。

## 3. Package / Module / Runtime 边界

`Package != Module != Service != Process`。所有 governed Module 统一提供 `install/uninstall/status/setup/docs/start/stop`；library 的 `start/stop` 可以是合法 no-op，并以 `runtimeStatus=NOT_APPLICABLE` 表达无独立 runtime。

## 4. Install / Uninstall

`platform install` 先完成 Workspace package set 的一次性 package-manager 同步，再按**冻结的产品部署顺序**调用 `Module.install`；Registry 返回顺序、npm packageName 字母序和 Runtime dependency depth 都不得决定用户部署轨迹。Package installed 不等于 Module installed。

冻结的 `Module.install` 前序为 `chrome-runtime → execution-browser-extension → agent-controller-dev → agent-product → agent-test-ops → agent-gateway → dev-tunnel`，其余当前模块继续按 Platform 的完整冻结安装序列执行；未知未来 Module 只能排在已冻结 Module 之后并使用稳定 `moduleRef` 顺序。Platform 在执行该顺序前仍必须构建 dependency graph，拒绝 unresolved / incompatible / cycle，但 graph 只做合同有效性校验，不改写 install 产品顺序。

`Module.install` 自闭环所有 deterministic materialization：路径、目录、loopback、token、SQLite、private runtime artifact 等。`platform setup/start` 继续使用真实 Runtime dependency topology；`platform uninstall` 按逆依赖顺序先调用 `Module.uninstall`，再移除 package dependency。Platform 不猜 Module-owned cleanup 语义。

## 5. Runtime Dependency / Shared Fact

`provides/requires` 表达 Module topology 与跨 Module Contract。Producer-owned shared fact 由 Module Contract 提供，禁止由 Platform 充当 config bus，也禁止让用户手工搬运系统可确定值。

## 6. Status / Setup / Docs

`platform status` 只聚合 `Module.status`。标准状态最小真源为 `setupStatus + runtimeStatus`，不再有 `configStatus/missingConfig`。

`platform setup` 的默认语义是**全量 setup**：按 dependency order 观察全部 discovered Module；`setupStatus=READY` 的 Module 跳过，其余 Module 均调用各自 `Module.setup`，不得在第一个 `ACTION_REQUIRED` 或 `FAILED` 处提前结束。Platform 最后一次性聚合本轮所有 Module 的结果，让 AI/用户一次看到当前全部可执行人工动作与机器 blocker。

`Module.setup` 的目标不是“描述配置”，而是**以最少用户操作、最少往返、最快达到 `setupStatus=READY`**。Module 必须先自动完成所有自身可确定、可执行、可验证的步骤；只有真正依赖用户选择或外部世界的动作才允许返回 `ACTION_REQUIRED`。不得要求用户搬运 Workspace path、loopback endpoint、token path、artifact path 或其它 Producer 已拥有的 shared fact。

每个 Module 的 `SETUP.md` 必须把 setup 写成最短闭环步骤。每个会影响 setup 进度的 Step 必须指向 package-owned executable/verify 入口；纯人工步骤也必须至少提供 package-owned prepare/verify 命令，使 AI 能准备材料、接受最小人工输入并机械验证完成。允许一个脚本一次完成多个可自动步骤，禁止为了形式把本可自动闭环的流程拆成多次人工交互。

`platform docs` 只聚合 `Module.docs`。标准知识文档只有 `DOCS.md` 与 `SETUP.md`；`CONFIGURATION.md` 不再是标准指导面。

## 7. Start / Stop

`platform start`：发现 Module → 构图 → 聚合 `Module.status` → 所有需要启动的 Module `setupStatus=READY` 后，按依赖顺序调用 `Module.start`。不存在独立 Platform preflight/validate 第二真源。

`platform stop`：按逆依赖顺序调用 `Module.stop`。Platform 不隐式 verify/repair。

## 8. Workspace 数据

`.proflow` 属于 Workspace / 用户数据与本地 metadata，可跨 uninstall/reinstall 保留；Module 自己决定其 owned artifact 的删除/保留规则。

## 9. 外部资源与 Carrier

Browser、ChatGPT Carrier、Dev Tunnel、Model Provider 等由 owning Module 自己表达 install/setup/status/docs/start/stop。Platform 只转发和聚合，不把外部世界逻辑搬进 CLI。

## 10. 收官边界

本轮只完成七命令管理面及其必要 Contract/Template/Conformance/Module seam/测试迁移。任何需要修改领域业务 API、状态机、service 算法或策略的问题立即记为 `OUT_OF_SCOPE_DOMAIN` 并 STOP，不得扩散整改。
