# 任务与编排领域｜领域模型与状态语义

> 本文是第一版业务语义真源。实现不得自行发明额外状态含义。

---

# 1. TaskGroup / Task Chain

## 1.1 定义

TaskGroup 是第一版“大型系统阶段任务链”的轻量容器。

典型场景：

```text
一个大型系统一次规划 10 个阶段 Task
→ 先全部创建
→ 但一次只允许一个 Task 实际进入工作
→ 当前 Task 成功后再释放下一 Task
```

第一版 `maxActiveTasks = 1`。这是组内约束，不是平台全局只能执行一个 Task。

## 1.2 状态

第一版 TaskGroup 至少：

```text
READY
ACTIVE
SUCCEEDED
```

`READY → ACTIVE` 必须来自一次明确的人工启动。

TaskGroup ACTIVE 后，Task Domain 只负责计算 / 校验哪些 Task 当前可执行。对于“一夜迭代”模式，人工授权发生在 TaskGroup 层；后续 Task 的实际启动可由扩展 / 自动化驱动，但仍必须调用正式 `startTask` 并通过 Task Domain 校验。

## 1.3 阻塞

若当前 Task 为 `WAITING / FAILED / PAUSED`，TaskGroup 停止继续释放后续 Task，直到人工处理。

# 2. Task

## 2.1 定义

Task 是一个可持久化、可启动、可暂停、可等待、可失败恢复、可完成或终止的工作目标。

Task 拥有：

```text
taskId
title
objective
status
version
planVersion
currentNodeId
TaskGroup membership（可选）
```

## 2.2 Task 状态

第一版：

```text
PENDING
READY
ACTIVE
WAITING
FAILED
PAUSED
SUCCEEDED
TERMINATED
```

### PENDING

Task 已存在，但尚未满足 v1 的**启动 readiness**。Extension `New Task` 先创建 PENDING Task，再为固定 Product / Controller-Dev / Test-Ops 三个 `agentPackageRef` 建立真实 Worker Conversation，并由 Product 在该 PENDING Task 下完成 Requirement 澄清。

PENDING 可以保存 Plan、Task-scoped Requirement/PRD、以及尚未补齐 workerRef/conversationLocator 的 TaskRoleBinding；但不能产生可执行 Node。**Task 不保存独立 human authorization/approval fact**。

### READY

Task 已满足确定性启动前置条件，但尚未开始业务 Node。v1 至少要求：

```text
required TaskRoleBinding 全部存在且 workerRef/conversationLocator 已绑定
Requirement 等 start-required TaskDocument 已正式存在
TaskGroup 前序条件满足（如有）
当前 Task 状态/版本合法
```

READY **不是“审批已记录”状态**。独立 Task 的用户“批准并开始”发生在 Extension/未来 Feishu human channel；确认后直接调用正式 `startTask`。Task 只重新校验 current readiness/version/idempotency，并执行 `READY → ACTIVE`。

TaskGroup 的 `startTaskGroup` 仍是显式 human command；已激活 TaskGroup 内后续成员是否由自动化调用 `startTask`，服从 TaskGroup 既有规则，不引入成员 Task Approval Entity。

### ACTIVE

Task 已真正开始，可以设置 `currentNodeId`、让当前 Node READY，并接受 `startNode / completeNode / waitNode / failNode`。

### WAITING

**业务级整 Task 停止。**

第一版不设计复杂“并行节点还能不能继续”的规则。

规则：

> **只要进入 WAITING，整个 Task 停。**

必须创建待处理 Message、记录 reason、让扩展 / 前端能发现，并等待人工处理。

典型原因必须是真正 workflow blocker，例如：

```text
BUSINESS_CONFIRMATION
EXTERNAL_INPUT_REQUIRED
REQUIREMENT_BLOCKED
```

Execution `QUEUED/RUNNING/WAITING_APPROVAL`、Collaboration `PENDING`、Carrier recovery 等异步事实**默认不自动把 Task/Node 变 WAITING**；它们继续由各 Owner 持有，结果 ready 后由 Task Observer 重新 WAKE/RESUME Worker。

### FAILED

表示技术 / 系统执行失败，例如 Execution Browser unavailable、本地服务失败、文件无法写入、Worker 执行异常。

`FAILED` **不是终态**。修复后可以通过受控 reopen / 重试机制继续。

### PAUSED

人工明确暂停 Task。

重要规则：

> **PAUSED 是 Task 级闸门，不要求逐个 Node 改为 PAUSED。**

例如：

```text
Task = PAUSED
Node = IN_PROGRESS
```

此时 Browser Extension 不继续驱动、Worker 不开始新动作、总控不继续推进 Task、写 API 必须拒绝非法推进。

恢复：`PAUSED → ACTIVE`，继续原 `currentNodeId` / 当前 run。

PAUSED 是协作式暂停，不是操作系统进程 kill。已经发出的外部动作可能自然结束，但其后续提交必须重新经过 Task 状态校验。

### SUCCEEDED

第一版完成条件：最后一个有效 Node `SUCCEEDED`，且 Task 当前不存在 `WAITING / FAILED / PAUSED`，然后 Task → SUCCEEDED，`currentNodeId = null`。

终态。

### TERMINATED

中文业务语义统一为“终止”，不使用 CANCELLED 作为主语义。

`Task → TERMINATED` 后不可 resume；后续若还要做，应创建新 Task。

# 3. Node

## 3.1 定义

Node 是 Task Workflow 中的**逻辑工作阶段，同时也是第一版最小可调度工作单元**。

第一版已经明确删除 WorkItem：

```text
Task
  ↓
Node
  ↓
具体 Worker
```

Node 不是人、Agent、Worker、浏览器页面或一次 Tool Execution。Node 代表当前 Task 的一个业务阶段，例如产品设计、研发 + 项管、测试 + 运维、上线验证。

## 3.2 不做并行 Node

第一版不存在并行 Node。即使现实中前端 / 后端可以并行，也统一归入当前复合角色“总控 = 项管 + 研发”的一个研发 Node。未来真实需要多 Worker / 多子工作后再抽 WorkItem / 并行 Node。

## 3.3 Node 状态

第一版：

```text
PENDING
READY
IN_PROGRESS
WAITING
FAILED
SUCCEEDED
TERMINATED
```

**没有 Node PAUSED。** Task PAUSED 控制整体执行。

- `PENDING`：尚未轮到该 Node。
- `READY`：满足条件，可以由 Task Observer 唤醒已经 Task-bound 的 Worker；正式 `startNode` 由 Worker 在收到 NODE_READY 后调用。
- `IN_PROGRESS`：当前 run 已绑定 Worker 并实际处理，但未完成 / 等待 / 失败。它不是“LLM 正在输出 token”。
- `WAITING`：Worker 明确声明真正 workflow/business blocker，Node / Task 才进入 WAITING 并创建 PendingMessage；普通 Execution/Peer/Approval pending 不自动映射为 WAITING。
- `FAILED`：当前 run 技术执行失败，Task 同步 FAILED。
- `SUCCEEDED`：当前 run 正常完成并满足必需输出文档校验。
- `TERMINATED`：Task 终止时尚未完成的 Node 可终止；已 SUCCEEDED 历史不反向改写。

---

# 4. 业务结果“不通过”与技术 FAILED 分开

测试工作正常执行并得到“产品不通过”，不是测试执行失败。

正确理解：

```text
测试执行本身 = 成功
业务结果 = NOT_PASSED
```

后续总控根据正式测试结果决定进入 WAITING 并 reopen 研发。

Execution Browser runtime 根本无法运行、测试脚本未执行、环境损坏等才属于 Node FAILED。

---

# 5. Node runNo

取消 WorkItem 后，每个 Node 使用 `runNo` 表示第几次实际执行。

```text
DEV runNo = 1 → SUCCEEDED
测试不通过 → reopen DEV
DEV runNo = 2 → READY
```

旧 run 不覆盖，由 `node_execution_history` 保存。

---

# 6. Worker 绑定

Node 保存：

```text
requiredAgentPackageRef
workerRef   # run-level actual worker, IN_PROGRESS 后写入
```

`requiredAgentPackageRef` 的值就是三个固定 Agent Package 的 `packageName`，它表示逻辑岗位；不得用真实 Custom GPT `roleRef/g-id` 表达“角色类型”。

TaskRoleBinding 以 `(taskId, agentPackageRef)` 为稳定键，至少保存：

```text
agentPackageRef
roleRef
workerRef
conversationLocator
```

其中 `roleRef / workerRef / conversationLocator` 都是跨域 opaque binding facts：Agent/Carrier 负责 identity 语义和验证，Task 只持久化“这个 Task 的这个逻辑岗位实际绑定到谁、如何恢复”。Task 永远不保存 tabId/frameId/windowId。

运行中 Node `workerRef` 不可修改。`reopenNode` 可以清空 Node run-level `workerRef`，但 **不得清除 TaskRoleBinding**；新 run 的 `startNode` 重新从同一 `requiredAgentPackageRef → TaskRoleBinding.workerRef` 解析原 Worker，因此 same task/node/role 默认复用原 Conversation。

---

# 7. 为什么没有 Claim

第一版正式删除 Claim。

原来的：

```text
Node → WorkItem → Claim → Worker
```

收敛为：

```text
Node → workerRef
```

`startNode` 原子完成 Task ACTIVE / Node READY / expectedVersion / idempotency 校验，并写 workerRef、startedAt、Node → IN_PROGRESS。

只有未来出现多人抢占、Lease、重新分配、多 Worker 争抢时再设计 Claim。

---

# 8. reopenNode：第一版循环 / 回退机制

第一版不实现通用 Workflow 循环引擎。所有跨 Node 回退使用显式 `reopenNode`。

例：

```text
产品       SUCCEEDED
研发       SUCCEEDED
测试       WAITING
上线       PENDING
```

总控确认后 `reopen 研发`：

```text
研发：runNo + 1，status → READY，workerRef → null
测试：status → PENDING，workerRef → null
上线：PENDING
Task：status → ACTIVE，currentNodeId → 研发
```

Node Execution History、Task Documents、Task Events 全部保留。

原则：`reopen` 只指定回到哪个 Node；之后按正常顺序重新向后推进。不建立自动 Edge 循环。

---

# 9. Node 内部业务循环

产品讨论、方案审计、多轮修改由当前 Worker 在同一个 Node 内完成。Task Domain 不把每次讨论都建成 Node。

---

# 10. Task Document

Task 相关正文属于 Task，不属于 Role 固定 Context。

```text
Requirement
PRD
Technical Design
Test Plan
Test Result
Release Result
```

这些随 taskId 走，不永久写进角色固定 Prompt / Memory。

---

# 11. Node 输入 / 输出文档

Plan 中每个 Node 必须显式声明：

```text
inputDocuments
outputDocuments
```

Worker 不自行遍历目录猜上下文。Task Service 根据 `taskId + nodeId` 组合当前 Node 所需 Markdown 内容。

---

# 12. Node 完成条件

普通 Node 流转没有人工审批。

完成条件：

```text
当前 Worker 正常完成
+
Plan 声明的必需 outputDocuments 均存在
=
Node SUCCEEDED
```

缺输出返回 `NODE_OUTPUT_MISSING`。

人工介入只在 Task / TaskGroup 开始、业务明确需要确认、Action 需要权限、Browser / Execution 明显异常或风险时发生。

---

# 13. Message

第一版 Message 状态只需：

```text
PENDING
ACKNOWLEDGED
```

`acknowledgeMessage` 只表示人已经看过 / 处理待办，不自动推进 Task。后续必须显式 `resumeTask` 或 `reopenNode`。

---

# 14. Event

Event 用于审计、调试、管理后台、问题排查、验收证据；不是当前状态真源。

当前状态必须查询：

```text
tasks
nodes
task_groups
```
