# 任务与编排领域｜关键流程与状态转换

---

# 1. 正常 Task 主流程

```text
Extension New Task
→ Task PENDING
→ declare fixed Product / Controller-Dev / Test-Ops participants
→ Browser Carrier CREATE/observe/bind 3 Workers（partial success只补缺失）
→ Product 在 PENDING Task 中完成 Requirement 并 putTaskDocument
→ requirement + required bindings + group prerequisites satisfied
→ Task READY
→ user confirms in Extension / future Feishu
→ startTask
→ Task ACTIVE + first business Node READY
→ Task Observer WAKE bound Worker
→ Worker startNode
→ Node IN_PROGRESS
→ Worker Turn / Execution / Collaboration
→ completeNode
→ next Node READY
→ ...
→ final Node SUCCEEDED
→ Task SUCCEEDED
```

第一版不引入自动 Graph Engine。下一 Node 按 `sequenceNo + 1`。Product requirement discussion 本身是 PENDING Task 的前置工作，不要求为了它制造一个可执行 Product Node；如某个真实 Task 需要正式 Product Node，可按普通 Node 定义，但不得与 J1 requirement clarification 混淆。
---

# 2. createTask

`createTask` 一次完成 Task + planVersion + ordered Nodes + initialDocuments，不拆 `createTask / createPlan / attachPlan`。

**新 Task 一律先进入 PENDING。** PENDING→READY 由 Task Owner 根据 start-required documents、固定三角色 TaskRoleBinding 和 TaskGroup prerequisites 确定性计算；不记录独立 human authorization fact。用户确认只发生在 READY 后调用 `startTask` 的 human channel。

---

# 3. startTask

原子效果：

```text
校验 Task == READY
校验 expectedTaskVersion
校验 group eligibility（如有）
校验 required TaskRoleBinding(agentPackageRef/roleRef/workerRef/conversationLocator) 已补齐

Task READY → ACTIVE
Task.version + 1
Task.startedAt = now

第一个 Node PENDING → READY
Node.version + 1

Task.currentNodeId = firstNodeId

写 Event
写 idempotency record
COMMIT
```

不得出现 Task 已 ACTIVE 但 first Node 仍 PENDING。

---

# 4. startNode

调用前必须已经存在 `TaskRoleBinding(requiredAgentPackageRef → roleRef/workerRef/conversationLocator)`。Task Observer 只 WAKE READY Worker；正式 `startNode` 由收到 NODE_READY 的 Worker 发起，调用方不提供任意 workerRef。

原子效果：

```text
校验 Task == ACTIVE
校验 Node == READY
按 Node.requiredAgentPackageRef 读取 TaskRoleBinding
校验 binding 存在且有效
校验 expectedTaskVersion
校验 expectedNodeVersion
校验 idempotency

Node.workerRef = TaskRoleBinding.workerRef
Node.status = IN_PROGRESS
Node.startedAt = now
Node.version + 1

Task.version + 1
NODE_STARTED Event
COMMIT
```

第一版没有 CLAIMED 中间状态。

---

# 5. completeNode

前置：Task ACTIVE、Node IN_PROGRESS、actor / worker 与当前 workerRef 合法、expectedVersion 正确、必需 outputDocuments 已存在。

事务：

```text
保存当前 run 的 execution history
Node → SUCCEEDED
Node.completedAt = now
Node.version + 1

若有下一个 Node：
  next PENDING → READY
  next.version + 1
  Task.currentNodeId = nextNodeId

若无下一个 Node：
  Task → SUCCEEDED
  Task.currentNodeId = null
  Task.completedAt = now

Task.version + 1

NODE_COMPLETED
NODE_READY 或 TASK_SUCCEEDED
idempotency record
COMMIT
```

---

# 6. waitNode

只用于真正 workflow/business blocker，例如业务确认、外部输入缺失或需求阻塞。Execution pending/WAITING_APPROVAL、Collaboration pending、Carrier recovery 默认不调用 waitNode。

请求包含 `waitType / reasonCode / message / relatedRef?`。

效果：

```text
Node → WAITING
Task → WAITING
创建 PendingMessage（仅业务 workflow blocker）
写 NODE_WAITING / TASK_WAITING Event
```

整个 Task 停止。

---

# 7. resumeTask

用于 `PAUSED → ACTIVE` 或 `WAITING → ACTIVE`。

若 current Node 是 WAITING：`Node WAITING → IN_PROGRESS`，runNo 和 workerRef 不变。

如果只是 Task PAUSED，Node 状态无需变化。

FAILED 不走普通 resume，优先显式 reopen。

---

# 8. failNode

只用于技术执行失败：

```text
Node → FAILED
Task → FAILED
记录 errorCode / errorMessage / retryable
创建必要 Event / Message
```

不自动重试。修复后 reopen 当前 Node，开始新的 runNo。

---

# 9. pauseTask

```text
Task ACTIVE / WAITING / FAILED
→ PAUSED
```

不逐个修改 Node。

所有执行方下一次推进前必须检查 Task.status。Task PAUSED 时禁止 startNode / completeNode / 新业务推进，扩展停止自动驱动。

---

# 10. terminateTask

```text
Task → TERMINATED
```

未完成 Node 可 TERMINATED；已 SUCCEEDED Node 保留；不可 resume。

---

# 11. reopenNode

例：

```text
1 产品       SUCCEEDED
2 研发       SUCCEEDED
3 测试       WAITING
4 上线       PENDING
```

执行 `reopenNode(node-dev)`：

```text
校验 Task 当前允许 reopen
校验目标 Node 属于当前 Task
校验 expectedTaskVersion

目标 Node:
  runNo + 1
  status = READY
  workerRef = null  # run-level reset；TaskRoleBinding 不变
  startedAt = null
  completedAt = null
  result / error 清空
  version + 1

所有 sequenceNo > target 的后续 Node:
  status = PENDING
  workerRef = null  # run-level reset；TaskRoleBinding 不变
  startedAt = null
  completedAt = null
  当前 result / error 清空
  version + 1

Task:
  status = ACTIVE
  currentNodeId = target
  version + 1

旧 history / document / event 全保留
NODE_REOPENED Event
COMMIT
```

原则：reopen 点以前 Node 保持已完成；reopen Node READY 新 run；之后 Node PENDING 等待重新经过。

---

# 12. 为什么不做通用循环

若直接允许 TEST → DEV → TEST → DEV，会立即引入循环计数、退出条件、旧 Node 状态、多轮 Artifact、死循环、自动回边、恢复点等复杂度。

第一版：跨 Node 回退 = `reopenNode`；Node 内多轮业务讨论 = Worker 自己处理。

---

# 13. 测试不通过推荐流程

```text
研发 Node SUCCEEDED
        ↓
测试 Node IN_PROGRESS
        ↓
测试工作执行成功
        ↓
写 test-result.md
业务结果 = NOT_PASSED
        ↓
waitNode(BUSINESS_CONFIRMATION, TEST_NOT_PASSED)
        ↓
Task WAITING
        ↓
总控读取测试结果
        ↓
人工 / 总控确认
        ↓
acknowledgeMessage
        ↓
reopenNode(研发)
        ↓
研发 runNo + 1
        ↓
重新向后推进
```

`TEST_NOT_PASSED != Node FAILED`。

---

# 14. Execution Approval / Browser Recovery 不自动映射 Task WAITING

```text
Execution WAITING_APPROVAL
→ Execution 保持自己的 durable approval fact
→ System Observer / UI channel 可提示人工处理
→ approval/resume/result ready
→ Task Observer 重新 WAKE 原 Worker

Carrier page recovery pending
→ Carrier/Execution recovery truth
→ current reality reconciliation
→ recovery success 后继续同一 Task run
```

只有 Requirement/业务确认/外部业务依赖等**真正 workflow blocker**，Worker 才通过 `waitNode` 把 Node/Task 置为 WAITING。Execution pending、Collaboration pending、Browser recovery 或 System Observer finding 默认不写入 Task WAITING，避免把跨域异步事实复制成第二真源。

---

# 15. TaskGroup / 一夜迭代

```text
TaskGroup READY
    ↓ 人工一次明确启动
TaskGroup ACTIVE

Task-01 READY
    ↓ startTask
ACTIVE → ... → SUCCEEDED

Task-02:
前序满足 → READY
扩展 / 自动化可继续调用 startTask

若任一 Task:
WAITING / FAILED / PAUSED
→ 整条链不继续释放后续 Task
→ 等人工处理
```

Task Domain 只负责 eligibility / status / sequence / maxActiveTasks，不负责打开浏览器或启动 GPT Conversation。


---

# 12. Owner fact → Task Observer → Carrier 的恢复循环

`completeNode/reopenNode` 只产生 Task owner facts；Execution Result READY / Peer Reply READY 仍分别属于 Execution/Collaboration。Task Observer 在 Extension background 读取这些 current facts，发现确定性下一步后请求 Carrier RESTORE/WAKE。Observer 不改 Task，不把日志或 Conversation reply 当 workflow truth。
